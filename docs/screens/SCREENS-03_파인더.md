## 03-A · 파인더

**목적** — 무엇을 마실지 모르는 사람에게 **질문 넷으로 3종을 고른다.** 탐색 화면이
"조건을 아는 사람"의 도구라면 이쪽은 그 반대다.

**진입** — 나브 탭 `03 파인더` · 탐색 결과가 너무 많을 때

### 질문 넷

| # | 질문 | 축 | 후보에 미치는 영향 |
|---|---|---|---|
| 1 | 오늘 원하는 도수는 | 도수 4구간 | **하드 필터** |
| 2 | 단맛은 얼마나 | 당도 | **하드 필터** (구간으로 묶음) |
| 3 | 어떤 향에 끌리나 | 향·맛 | **점수만** — 후보를 줄이지 않는다 |
| 4 | 선호하는 기주가 있나 | 기주 | **하드 필터** (묶음) |

향을 하드 필터로 걸지 않는 것이 의도다. 넷을 전부 교차하면 후보가 0으로 떨어지는 조합이
너무 많고, 파인더는 **답을 내는 화면**이라 빈손으로 끝나면 존재 이유가 없다.

### 도수는 탐색 필터와 **같은 정의**를 쓴다

`FR-SEARCH-004`가 요구하고 [ADR-0003](../decisions/ADR-0003-graph-source-and-abv-bands.md)이
"탐색 필터와 취향 파인더가 이 정의를 공유한다"고 못박은 지점이다.

```
질문 1의 선택지 = ABV_BANDS 를 그대로 편 것
  무알콜 / 가볍게 / 적당히 / 독하게      ← 파인더 표기 (구어체)
  논알콜 / 저 ~10% / 중 10–20% / 고 20%~  ← 탐색 표기
  na    / low     / mid       / high      ← 주소·API 어휘 (같다)
```

**파인더 전용 도수 상수를 만들지 않는다.** 따로 두면 반드시 어긋나고, 어긋나면 파인더가
"가볍게"로 추천한 것을 탐색의 "저 ~10%"에서 못 찾는다 — 두 화면이 서로를 부정한다.
구간 경계(`(하한, 상한]`)는 `abvBandOf()` 한 곳에만 있고 서버도 같은 경계를 쓴다.

### 레이아웃

```
.page-head    취향 파인더   4 questions
──────────────────────────────── 2px ───────────────────────────
┌ aside (220px) ────────┬ .quiz-card ──────────────────────────┐
│ 진행 PROGRESS         │  QUESTION 2 / 4                      │
│ ── 2px ──             │  단맛은 얼마나 들어가길 원하시나요?   │
│ 01 오늘 원하는 도수    │  당도는 4단계로 색인되어 있습니다.     │
│    독하게             │  ┌──────────┐ ┌──────────┐          │
│ 02 단맛은 얼마나 ◀    │  │단맛 절대  │ │살짝 달콤  │          │
│    —                  │  │사절  Dry  │ │Semi-Dry  │          │
│ 03 어떤 향에          │  └──────────┘ └──────────┘          │
│ 04 선호하는 기주       │  ┌──────────┐ ┌──────────┐          │
│                       │  │달콤함 선호│ │상관없음   │          │
│ 현재 후보 12종         │  └──────────┘ └──────────┘          │
│                       │  ── 1px ──                           │
│                       │  [← 이전]        [처음부터 RESTART]  │
└───────────────────────┴──────────────────────────────────────┘
```

진행 표시는 왼쪽에 계속 남는다. 답한 질문에는 고른 값이 붙어 **어디까지 왔고 무엇을
골랐는지**를 화면을 떠나지 않고 볼 수 있다.

### 현재 후보 수 — 이 화면의 계기판

질문마다 남은 후보 수가 왼쪽 아래에 있다. 숫자가 줄어드는 것이 보여야 질문에 답할 이유가
생기고, [SPEC-10 §4.4](../spec/SPEC-10_계측_이벤트.md)의 `finder_step.candidateCount`가
재려는 것도 같은 값이다 — **1~2로 급감하면 질문이 너무 좁게 거른다는 뜻이다.**

**후보가 0이 되면 그 자리에서 알린다.** 남은 질문에 계속 답하게 두면 마지막에 가서야 빈
화면을 본다. 되돌아갈 곳(이전 단계)과 다시 시작하는 길을 함께 준다.

### URL

답과 단계가 쿼리스트링에 실린다. 새로고침해도 그 자리이고, 링크를 주면 같은 화면이 열린다.

```
/finder?abv=high&sweet=dry&flavor=smoky&base=whisky&step=4
```

| | |
|---|---|
| `abv` | **탐색 필터와 같은 어휘다** (`na`·`low`·`mid`·`high`) — `FR-SEARCH-004` |
| `sweet` | `dry` · `semi_dry` · `sweet` · `any` — **파인더가 묶은 선택지** |
| `flavor` | 향 태그 슬러그. 점수에만 반영된다 |
| `base` | `any` · `clear`(진·보드카) · `whisky` · `warm`(럼·데킬라·전통주) — **묶음** |
| `step` | 0~4. 답변 수를 넘지 못한다 — 주소를 손으로 고쳐도 흐름이 어긋나지 않는다 |

> **`sweet`·`base`는 탐색 화면의 같은 이름과 뜻이 다르다.** 탐색의 `sweet=semi_dry`는 그
> 한 단계지만 파인더의 것은 가운데 두 단계를 덮는다. `base=clear`는 탐색에 아예 없는 값이다
> (탐색은 `base=gin,vodka`로 적는다). **두 화면의 주소를 서로 옮겨 붙이지 않는다.**
> 도수만 같은 어휘인 것이 우연이 아니라 `FR-SEARCH-004`의 요구다.

색인은 받되 **canonical은 답 없는 `/finder`로 고정**한다. 답이 붙은 주소는 같은 화면의
다른 상태일 뿐이라 조합마다 색인되면 중복 콘텐츠가 된다 (`PRIN-P06` · [G-33](../prd/GAPS.md#g-33)).

### 결과

마지막 질문에 답하면 상위 3종이 나온다. 카드마다 순위·매칭 점수(62~98)·기주·당도·도수와
**왜 골랐는지 한 줄**이 붙는다. 1위 카드만 테두리가 accent 2px다.

점수는 62점에서 출발해 향 일치(+22, 부분 일치 +14/+10) · 당도 근접(최대 +10) · 고도수
구간 안에서의 순위(+6) · 기주 지정(+4)을 더한다. **100점을 주지 않는다** — 취향은 계산으로
확정되지 않고, 98이 상한인 것이 그 태도다.

### 상태

| 상태 | 표현 |
|---|---|
| 진행 중 후보 0 | `조건에 맞는 항목이 없습니다.` + 이전 단계·처음부터 안내 (`.quiz-dead-end`) |
| 결과 0 | `조건을 모두 만족하는 항목이 없습니다` / `도수나 당도 조건을 넓혀 다시 시도해보세요.` |
| 로딩 | 없다 — 코퍼스가 이미 브라우저에 있다 |

### 렌더링

[SPEC-05 §4](../spec/SPEC-05_아키텍처.md) 표에 `/finder`가 없다. **셸은 정적, 진행은
브라우저에서** 한다. 코퍼스는 탐색 화면과 같은 목록을 페이지가 한 번 받아 넘기고,
단계 전환에 **서버 왕복이 없다** (`NFR-P-02`).

### 접근성

| 요구 | 어떻게 |
|---|---|
| `NFR-A-04` 키보드 | 선택지가 전부 `<button>`이다. Tab → Enter로 네 단계를 끝까지 지난다 |
| `NFR-A-05` 포커스 | 전역 `:focus-visible` 아웃라인 2px |
| `NFR-A-08` 색만으로 금지 | 고른 선택지에 **`선택함`** 글자가 붙는다. 테두리 색만 바뀌지 않는다 |
| 진행 안내 | 후보 수 칸이 `aria-live="polite"` — 답할 때마다 남은 수와 질문 번호를 읽는다 |
| 후보 0 안내 | `role="status"` |

### 계측

[SPEC-10 §4.4](../spec/SPEC-10_계측_이벤트.md) `finder_step`(`step`·`answered`·`candidateCount`)은
**[이슈 049](https://github.com/cacaocoffee/mut/issues/51)가 심는다.**
기반(이슈 035)이 아직 없어 이 화면에는 호출 지점만 비어 있다.
`step=4` 도달이 완주 판정이고 `finder_complete`는 두지 않는다.

### 하지 않는 것

| | 왜 |
|---|---|
| 파인더 결과 저장 | Phase 1a 범위 밖 (`FR-USER-004`는 API만 — [G-18](../prd/GAPS.md#g-18)) |
| 질문 추가 | 넷도 이탈이 걱정이다. 완주율(`step=4`/`step=1`)이 존치 판단 근거다 |
| 향을 하드 필터로 | 후보 0이 급증한다. 점수로만 반영한다 |

## 03-B · 내 술장

> **폐기 (2026-08-20 · [ADR-0010](../decisions/ADR-0010-articles-over-my-bar.md))** —
> 화면 구현을 걷어냈고 로드맵에서도 뺐다. 아래는 기록이다.

**목적** — 가진 재료를 담으면 **지금 만들 수 있는 것**과 **하나만 더 있으면 되는 것**을
되짚는다 (`R-F2.2-1`·`2`).

**경로** — `/my-bar` · `noindex`

담은 것에 따라 내용이 통째로 달라지는 화면이라 탐색 필터와 같은 성격이다
(`PRIN-P06` · `NFR-S-02`). 색인되면 남의 술장이 검색 결과에 뜨는 셈이 된다.

### 구성

| 블록 | 내용 | 근거 |
|---|---|---|
| **재료 찾기** | 이름·별칭 자동완성. 연달아 담는다 | — |
| 재료 체크리스트 | 카테고리별. **가니시는 내지 않는다** | `R-F2.2-5` |
| 지금 만들 수 있는 것 | 칵테일 카드 그리드 | `R-F2.2-1` |
| 재료 하나만 더 있으면 | 줄 목록 + **빠진 재료 이름** | `R-F2.2-2` |
| **가진 재료가 들어가는 것** | 두 칸 이상 빈 것 + **다음에 살 것** | `R-F2.2-2` 의 연장 |
| 빈 술장 | 무엇을 하는 곳인지 + 권하는 재료 6개 | — |

### 찾기와 훑기를 둘 다 둔다

고를 수 있는 재료가 59종이다. 이름을 아는 사람에게는 치는 편이 빠르고, 모르는 사람은
훑어야 한다 — 훑다 보면 있는 줄도 몰랐던 것이 눈에 든다. 둘 다 남긴다.

자동완성의 조작 문법과 생김새는 [통합 검색의 `SearchBox`](./SCREENS-01_칵테일.md)에서
가져온다 — 같은 사이트에서 두 자동완성이 다르게 움직이면 안 된다. **다른 것은 고른 뒤다**:
저쪽은 한 번 골라 그 화면으로 떠나고, 여기는 입력만 비우고 목록을 열어 둔 채 연달아 담는다.

별칭으로도 찾힌다 — `코앵트로` 를 쳐도 `쿠앵트로` 가 나온다. 마스터가 그 흔들림을
이미 들고 있어서(`ingredients.ts` 의 `aliases`) 찾기가 목록을 다시 만들지 않는다.

### 뭘 사야 하나에 답한다

「만들 수 있는 것」과 「하나만 더」는 재료가 적은 사람에게 거의 비어 있다. 캄파리 · 진 ·
카시스만 있으면 둘을 합쳐 두 줄이고, 그러면 **뭘 사야 하는지 알 방법이 없다.**

세 번째 묶음이 두 칸 이상 빈 것까지 펼치고, 그 위에 **다음에 살 것**을 적는다.
목록에서 빠진 재료가 겹치는 것을 사람이 세지 않게 코드가 센다.

```
다음에 살 것   스위트 베르무트 바로 1잔 · 토닉워터 바로 1잔
              설탕 시럽 5잔이 기다림 · 드라이 베르무트 4잔 · 레몬 주스 4잔
```

`바로 N잔` 은 그것만 사면 즉시 만들 수 있게 되는 수, `N잔이 기다림` 은 아직 멀어도 그
재료가 막고 있는 수다. 세 묶음은 서로 겹치지 않는다 — 빈 칸 0개 · 1개 · 2개 이상.

### 가니시를 빼는 것이 요체다

`R-F2.2-5` — *"가니시와 얼음, 물은 보유 재료 판정에서 제외한다. **이걸 요구하면 매칭이
거의 안 된다.**"* 데이터에서 레몬 필(8) · 오렌지 필(7) · 민트(2)가 상위권이라, 빼지 않으면
오렌지 껍질이 없어서 네그로니를 못 만든다는 답이 나온다.

빼는 판단은 `countsForStock` 한 곳에서 한다 — 화면이 다시 거르지 않는다. 판정에 안 쓰는
것을 고르게 하면 "체크했는데 왜 결과가 그대로냐" 가 되므로 **목록에도 내지 않는다.**

### 「하나만 더」가 이 화면의 값이다

만들 수 있는 것만 보여 주면 재료가 적은 사람에게는 빈 화면이고, 그 자리에서 나간다.
PRD 가 `R-F2.2-2` 를 "체류와 재방문의 핵심 동인" 이라고 적은 이유다. **무엇이 빠졌는지**
까지 적는다 — 적지 않으면 목록이 아니라 놀림이다.

택일로 적힌 줄(`버번 또는 라이`)은 "둘 중 아무거나" 로 읽고 그렇게 표시한다.

### 로그인 없이 쓴다

`R-F2.2-4`. 담은 것은 `localStorage["mut:stock"]` 에 있다. 재료를 스무 개 체크하게 해 놓고
로그인을 요구하면 그 자리에서 나간다.

`GET`·`PUT /me/stock` 은 계약에 아직 없다 (`/me/bookmarks`·`/me/collections` 뿐).
인증이 붙으면 이 값이 첫 동기화 대상이고, **화면 주소는 그대로 둔다** — 로그인 여부로
주소가 바뀌면 보내 둔 링크가 깨진다.

### 하지 않는 것

| | 왜 |
|---|---|
| 부족 재료의 구매처 링크 | `R-F2.2-3` — 국내 유통 데이터가 없다 (01-D 와 같은 이유) |
| 서버 동기화 | 인증이 붙은 뒤. `user_stock` 은 Phase 2 다 |
| 재료를 몇 병 갖고 있나 | 역검색에 필요 없다. 있냐 없냐만 본다 |
