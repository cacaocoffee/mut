# ADR-0002 · 분류 체계는 시안을 기준으로 PRD가 보강한다

| | |
|---|---|
| 상태 | 확정 |
| 일자 | 2026-08-06 |
| 대체 | PRD v1.0 `R-F1.1-5`(당도 3단계), 6.3 향·맛 태그표, 5.1 `soju` 슬러그 |
| 관련 갭 | [G-01](../prd/GAPS.md#g-01) · [G-02](../prd/GAPS.md#g-02) · [G-03](../prd/GAPS.md#g-03) · [G-04](../prd/GAPS.md#g-04) |

## 맥락

PRD 5장·6장과 시안이 "칵테일 한 건을 어떻게 색인하는가"에 대해 네 군데에서 다른 말을 했다.
넷은 한 질문의 조각이라 따로 정하면 어긋나므로 한 번에 묶어 결정했다.

## 결정

### 1. 당도는 4단계를 유지한다 (G-01)

`드라이 · 세미 드라이 · 세미 스위트 · 스위트`. PRD `R-F1.1-5`의 3단계를 폐기한다.

3단계로 줄이면 네그로니(0)와 김렛(1)이 같은 칸에 들어간다. 이 둘은 실제로 다른 음료다.
부수적으로 시안의 당도 태그 색 스케일이 4칸 전제(중립 → accent-2 → accent-200 → accent 채움)라
재디자인이 필요하고, 파인더 점수식의 보정(`sweet === 1 ? 1.5 : sweet`)도 다시 짜야 한다.
PRD 쪽을 고치는 편이 싸고 정확하다.

### 2. 향·맛 태그는 양쪽의 합집합 10개로 한다 (G-02)

```
citrus  sour  fruity  floral  herbal  spicy  smoky  bitter  nutty  creamy
```

PRD 6.3의 9개 중 `시트러스`가 산미를 흡수하고 있었는데, 시안은 `citrus`(향)와 `sour`(맛)를
분리했다. **분리를 채택한다** — 위스키 사워는 `sour`지만 시트러스 향이 주인공이 아니다.
현재 파인더 점수식도 이 분리를 전제로 `citrus` 선택 시 `sour`에 부분 점수(+14)를 준다.

PRD에만 있던 `floral · nutty · creamy`는 **추가한다.** 커버리지 문제다.
에스프레소 마티니에 `nutty`가 없으면 "커피 향" 검색이 불가능하고, 24종을 500종으로 늘리면
플로럴(엘더플라워·바이올렛) 계열이 반드시 들어온다.

`R-F1.2-1`의 **최대 3개 제한은 유지한다.** 보강한 4건은 전부 3개 이내다.

| 항목 | 이전 | 이후 | 근거 |
|---|---|---|---|
| 에스프레소 마티니 | bitter, fruity | + `nutty` | 커피·카카오 계열 |
| 마이 타이 | fruity, citrus | + `nutty` | 오르자(아몬드)가 향의 중심 |
| 위스키 사워 | sour, citrus | + `creamy` | 달걀 흰자 |
| 막걸리 콜라다 | fruity | + `creamy` | 코코넛 크림 |

`floral`은 현재 24종에 해당 항목이 **0건**이다. enum에는 두되 필터 UI에는 노출하지 않는다(아래 4항).

### 3. 스타일 축을 도입하고 24종을 색인한다 (G-03)

`R-C-1`이 "세 축은 모든 칵테일에 필수값"이라고 했는데 스타일이 **아예 없었다.**
`R-C-3`의 배리에이션 추천도 `style_primary` 일치를 1순위로 쓰는데, 그게 없으니
상세 화면의 관련 추천이 기주만 보고 있었다 — `R-C-3`가 "NULL이면 태그 매칭으로 퇴화한다"고
경고한 바로 그 상태다.

`styles: StyleKey[]` + `stylePrimary: StyleKey`를 필수 필드로 추가했다. 색인 결과:

| 스타일 | 수 | 항목 |
|---|---|---|
| `highball` | 8 | 진토닉 · 모스코 뮬 · 블러디 메리 · 모히토 · 다크 앤 스토미 · 팔로마 · 소주 하이볼 · 시트러스 슈럽 |
| `sour` | 7 | 김렛 · 사우스사이드 · 코즈모폴리탄 · 위스키 사워 · 페니실린 · 다이키리 · 마르가리타 |
| `spirit-forward` | 6 | 네그로니 · 마티니 · 올드 패션드 · 맨해튼 · 불바디에 · 문배 올드 패션드 |
| `creamy` | 2 | 에스프레소 마티니 · 막걸리 콜라다 |
| `tiki` | 1 | 마이 타이 |

복수 스타일을 가진 항목은 3건이다 — 모히토(`highball` + `sour`), 마이 타이(`tiki` + `sour`),
막걸리 콜라다(`creamy` + `tiki`). 이 셋이 복수 축이 실제로 동작하는지 확인해주는 표본이다.

`spritz · hot · frozen · shot`은 enum에 두되 현재 해당 항목이 없다.

### 4. 기주 슬러그를 정리한다 (G-04)

표시명은 시안, 슬러그는 PRD를 따르되 두 곳을 고친다.

| 표시명 | 슬러그 | 비고 |
|---|---|---|
| 진 / 보드카 / 위스키 / 럼 | `gin` `vodka` `whisky` `rum` | 그대로 |
| **데킬라 · 메즈칼** | `agave` | 표시명을 PRD 범위에 맞춰 넓힘 |
| **전통주** | **`korean`** | PRD는 `soju`였다. 막걸리·문배주를 소주로 부르는 건 부정확하고, PRD 5.1 스스로 이 축을 "국내판 정체성 축"이라 했다 |
| 무알콜 | `non-alcoholic` | 그대로 |
| 브랜디 / 리큐르 / 와인 · 스파클링 | `brandy` `liqueur` `wine` | enum에만 존재, 현재 0건 |

슬러그는 그대로 카테고리 URL이 된다. 노출된 뒤에 바꾸면 리다이렉트를 깔아야 하므로
항목이 없는 지금 정리했다.

### 5. enum은 완전하게, UI는 코퍼스만

카테고리 URL의 정본이므로 enum은 PRD 기준으로 완전히 둔다(기주 10종, 스타일 9종, 향 10종).
하지만 필터 UI에 0건짜리 칩을 늘어놓으면 고장난 것처럼 보인다.

그래서 화면은 **코퍼스에 있는 값만** 돌고, **그 안에서 조합 때문에 0이 된 값만** 비활성
처리한다. `R-F2.1-2`가 말하는 0건은 후자다 (스피릿 포워드 × 셰이크 = 0건 같은 경우).

그 목록을 **패싯 응답이 준다** (이슈 040). `facetCounts()`는 코퍼스에 없는 값의 키를 아예
넣지 않고, 화면은 받은 키를 돌며 칩을 만든다 — 서버 `GET /cocktails/facets`도 같은 규칙이라
(`FacetReader`) 계산 위치가 바뀌어도 이 문단은 그대로다. 프로토타입 코퍼스를 세는
`BASES_IN_CORPUS` · `STYLES_IN_CORPUS` · `FLAVORS_IN_CORPUS`는 `npm run check`가 쓴다.

## 결과

- `packages/domain/src/types.ts`가 세 축의 정본이 됐다.
- `packages/domain/src/validate.ts`가 불변식을 강제한다 — 3축 필수, `stylePrimary ∈ styles`,
  향 태그 1~3개, 무알콜↔도수 정합성. `npm run check`로 돌고 CI에서 빌드를 세운다.
  24종일 때는 눈으로 보이지만 500종이 되면 이것 말고는 확인할 방법이 없다.
- 상세 화면의 관련 추천이 `relatedCocktails()`로 바뀌어 `stylePrimary` 1순위 · 기주 2순위로 동작한다.
- 탐색 화면에 스타일 필터가 추가됐고 URL 파라미터 `?style=`로 공유된다.
- 스펙 스트립이 4칸에서 5칸이 됐다 (ABV · STYLE · GLASSWARE · TECHNIQUE · SWEETNESS).

## 남은 것

`/cocktails/base/<slug>/` · `/cocktails/style/<slug>/` · `/cocktails/method/<slug>/`
카테고리 페이지는 아직 만들지 않았다. 슬러그는 확정됐으니 라우트만 붙이면 된다.
`R-C-2`에 따라 **단일 축 경로만** 색인하고 축 조합 경로는 만들지 않는다.
