## 1. 시그니처는 에디터가, 전체 메뉴판은 파트너가

### 맥락

`PRIN-P01`은 칵테일↔바 양방향 순환을 이 제품의 해자로 규정했다. 그 순환의 물리적 구현이
`BarMenuItem.cocktail_id`이고, PRD 6.1은 "이 칵테일을 마실 수 있는 바"를 **핵심 훅**으로 표시했다.

문제는 **누가 그 데이터를 넣느냐**다. PRD가 답하지 않았다.

파트너만 입력하게 하면 논리적으로 깔끔하다 — 제휴 가치가 선명하고 정확도·최신성이 높다.
그런데 6개월 목표가 유료 제휴사 30곳이다. **런치 시점에는 파트너가 0에 가깝고,
그러면 "이 칵테일을 마실 수 있는 바"가 전부 비어 있다.**

핵심 훅이 빈 채로 출시되면 그래프 가설을 검증할 방법이 없다. 그런데 그 가설의 검증이
Phase 1의 존재 이유다(SPEC-01 §8). 자기모순이다.

반대로 에디터가 전체 메뉴판을 취재하면 커버리지는 최대가 되지만, 메뉴는 시즌마다 바뀐다.
에디터 1명으로 바 100곳의 전체 메뉴를 최신으로 유지하는 건 불가능하고,
틀린 메뉴를 노출하는 건 신뢰 손상이다 — `PRIN-P03`이 금지하는 종류의 부정확이다.

### 결정

**입력 주체를 메뉴 종류로 나눈다.**

| | 입력 주체 | 대상 | 검증 |
|---|---|---|---|
| `is_signature = true` | **에디터 취재** | **미제휴 바 포함** | 바당 2~4건, 연 1회 |
| `is_signature = false` | `partner` 등급 이상만 | 제휴 바 | 바가 직접 관리 |

근거는 **시그니처가 바의 정체성이라 잘 바뀌지 않는다**는 것이다. 대상 건수도 적다 —
바당 2~4건이면 100곳에서 200~400건이고, 이건 에디터 1명이 취재하면서 자연히 쌓이는 양이다.
어차피 에디터 노트(`FR-BAR-007`)를 쓰려면 그 바에 가야 한다.

### 결과

- 런치 시점에 그래프가 비지 않는다. `PRIN-P01`을 Phase 1에 검증할 수 있다.
- **미제휴 바가 그래프에 들어오는 것 자체가 영업 미끼가 된다** — 이미 노출되고 있는 바에게
  "전체 메뉴판과 시그니처 레시피 정식 등재"를 파는 쪽이, 아무것도 없는 상태에서 파는 것보다 쉽다.
  `R-F3.1-5`가 커버리지를 영업 파이프라인으로 규정한 것과 같은 논리다.
- 시그니처 검증 주기(연 1회)가 `hours_verified_at`(90일)보다 길다. 의도적이다 —
  영업시간은 자주 바뀌지만 시그니처는 그렇지 않다.

### 되돌리는 조건

에디터 취재한 시그니처의 오류율이 눈에 띄게 높아지면(바가 시그니처를 자주 교체하는 신에서
그럴 수 있다) 검증 주기를 반기로 줄이거나 `verified` 등급에 수정 요청 권한을 준다.

## 2. 도수 필터는 4구간 칩으로 한다

### 맥락

같은 것을 세 곳이 다르게 정의하고 있었다.

| 출처 | 정의 |
|---|---|
| PRD 7.1 | 4구간 — 논알콜 / 저 ~10% / 중 10–20% / 고 20%~ |
| 시안 · 현재 코드 | 0~45 연속 슬라이더 (상한 필터) |
| 파인더 4번 질문 | 또 다른 4구간 — 0 / ~14 / ~25 / 25%+ |

셋 다 살려두면 같은 사용자가 세 화면에서 다른 답을 본다.

### 결정

**PRD의 4구간을 정본으로 하고, 탐색 필터와 파인더가 같은 정의를 공유한다.
연속 슬라이더는 버린다.**

결정적인 이유는 취향 문제가 아니라 **스펙 정합성**이다.

`R-F2.1-2`는 모든 필터 값 옆에 실시간 결과 개수를 표시하고 0건이면 비활성 처리하라고 요구한다.
PRD가 "초기부터 넣지 않으면 나중에 UI를 다시 짜야 한다"고 못박은 항목이다.

**연속 슬라이더에는 값별 카운트를 붙일 수 없다.** 45개 눈금마다 숫자를 달 수도 없고,
0건인 눈금을 비활성화할 수도 없다. 슬라이더를 유지하면 도수만 `R-F2.1-2`의 예외가 되고,
그러면 "모든 필터 값"이라는 요구가 무너진다.

### 결과

- 시안의 슬라이더 UI를 포기한다. 시안이 틀렸다기보다, 시안은 패싯 카운트 요구를 몰랐다.
- 구간 정의는 한 곳에만 둔다 — `abvBandOf()`. 탐색 필터 · 파인더 · 패싯 카운트가 전부 이걸 쓴다.
  경계를 바꾸려면 이 함수만 고친다.
- 파인더 1번 질문의 라벨은 구어체(`무알콜`·`가볍게`·`적당히`·`독하게`)로 두되
  **구간 정의는 탐색 필터와 동일**하다. 라벨과 정의를 분리한 것이 요점이다.
- `matchScore`의 도수 가산점은 구간 **안에서의** 순위 조정용으로 축소했다.
  구간이 이미 하드 필터라 구간 일치에 다시 점수를 주는 건 의미가 없다.
  `high`만 위가 열려 있어 폭이 넓으므로 28% 이상에 +6을 남겼다.

### 구현 확인 (2026-08-06)

```
논알콜  1종 · 저 ~10%  2종 · 중 10–20%  8종 · 고 20%~ 13종   합 24 ✓
```

`npm run check`가 구간 합계와 코퍼스 크기 일치를 검증한다 — 구간에 구멍이 생기면 빌드가 선다.

의도한 동작이 실제로 나온다. 기주를 `위스키`로 좁히면 도수 카운트가
`{na:0, low:0, mid:1, high:4}`가 되어 **논알콜·저도수 칩이 자동 비활성화**된다.
슬라이더로는 만들 수 없던 동작이고, `R-F2.1-2`가 요구한 바로 그것이다.

### 되돌리는 조건

코퍼스가 커져 구간 안의 분포가 뭉치면(예: "고 20%~"에 절반이 몰림) 구간을 더 쪼갠다.
슬라이더로 돌아가지는 않는다 — `R-F2.1-2`가 유효한 한 같은 문제가 반복된다.
