## 근거

**`FR-SEARCH-004`**: 취향 파인더의 도수 질문도 **`FR-SEARCH-003`과 같은 구간 정의**를 쓴다 (ADR-0003)

**ADR-0003 도수 4구간** — `packages/domain/src/types.ts` 주석:

> 도수 4구간. 연속 슬라이더를 쓰지 않는 이유는 `R-F2.1-2`가 모든 필터 값에 결과 개수를 요구하는데 **슬라이더 눈금에는 카운트를 붙일 수 없기** 때문이다 (ADR-0003).
> **탐색 필터와 취향 파인더가 이 정의를 공유한다.**

**SPEC-10 §4.4 `finder_step`** (이슈 035)

| payload | |
|---|---|
| `step` | 1~4 |
| `answered` | 선택값 |
| `candidateCount` | 남은 후보 수 |

> `finder_complete`는 별도 이벤트로 두지 않는다. **`step=4` 도달로 완주를 판정한다.**
>
> 어느 질문에서 이탈하나. **`candidateCount`가 1~2로 급감하면 질문이 너무 좁게 거른다는 뜻이다.**

**SPEC-10 §6.1 파생 지표**: **파인더 완주율** = `step=4` / `step=1` → **파인더 존치 판단**

**SPEC-01 §6**: 프로토타입의 3개 화면 중 하나가 파인더다. **디자인 시스템 성립 증명과 분류 3축·패싯 카운트 동작 검증**이 그 역할이었다

**SPEC-05 §4**: 파인더 경로가 렌더링 전략 표에 **없다**. ⚖️ `/finder`는 클라이언트 상호작용이 전부라 **CSR 또는 정적 셸**이 자연스럽다 + GAPS

**`NFR-A-04`**: 모든 인터랙션이 **키보드로 도달·조작 가능** — 배포 차단
**`NFR-P-02`**: INP ≤ 200ms — 배포 차단

**현재**: `apps/web/components/finder-screen.tsx` + `app/finder/page.tsx` — 동작하는 프로토타입

## RED

### 도수 구간 공유 (`FR-SEARCH-004` — 요체)

1. `파인더_도수_질문이_4구간이다`
2. `구간_정의가_탐색_필터와_동일하다` — **같은 `AbvBand` 타입을 쓴다**
3. `구간_경계가_서버와_같다` (이슈 018 RED 15~20)
4. `연속_슬라이더가_없다` (ADR-0003)
5. `구간_정의가_한_곳에서_온다` — 파인더 전용 상수 부재. **두 곳에 두면 어긋난다**

### 단계 진행

6. `4단계로_구성된다` — SPEC-10 §4.4의 `step` 1~4
7. `각_단계에서_후보_수가_표시된다` — `candidateCount`
8. `이전_단계로_돌아갈_수_있다`
9. `단계마다_URL이_바뀌는가` ⚖️ — 공유 가능성 vs 단순함. **보수적으로 쿼리스트링 반영** + GAPS
10. `마지막_단계에서_결과가_나온다`
11. `후보가_0이면_안내가_나온다` — 막다른 길 방지

### 필터 로직 공유 (SPEC-01 §6)

12. `search_ts의_파인더_로직을_쓴다` — 유지 대상
13. `탐색_필터와_같은_코퍼스를_쓴다`
14. `파인더_결과가_같은_조건의_탐색_결과와_일치한다` — 두 경로가 다른 답을 내면 안 된다

### 계측 (SPEC-10 §4.4 — 이슈 035)

16. `step과_answered와_candidateCount가_담긴다`

18. `이탈해도_직전_단계까지_기록된다`

### 접근성 (`NFR-A-04`·`A-05`·`A-08`)

## GREEN

### 도수 구간 공유 (RED 1~5 — 이 이슈의 핵심)

```ts
// ADR-0003 · FR-SEARCH-004 — 탐색 필터와 파인더가 같은 정의를 공유한다
import { ABV_BANDS } from "@repo/domain";   // 한 곳
```

**파인더 전용 도수 상수를 만들지 않는다** (RED 5). ADR-0003이 "탐색 필터와 취향 파인더가 이 정의를 공유한다"고 명시한 이유는, **따로 두면 반드시 어긋나기** 때문이다.

이슈 037에서 `AbvBand`가 생성 타입으로 바뀌었으므로, 파인더도 그것을 쓴다.

### 기존 코드 유지 (SPEC-01 §6)

`finder-screen.tsx`와 `search.ts`의 파인더 로직을 **그대로 쓴다.** 데이터 출처만 API로 (이슈 040과 동일).

### 계측 (RED 15~18)

```ts
// SPEC-10 §4.4 — step=4 도달로 완주 판정. finder_complete 없음
track("finder_step", { step, answered, candidateCount });
```

`candidateCount`가 SPEC-10 §4.4의 판단 근거다 — "**1~2로 급감하면 질문이 너무 좁게 거른다**".

### 렌더링 (⚖️ RED 9)

SPEC-05 §4 표에 `/finder`가 없다. **CSR로 두되 셸은 정적**으로. 색인 대상이 아니다(결과가 개인화된 탐색이라 `PRIN-P06`의 필터 성격).

⚖️ `noindex`를 붙일지 GAPS 등재.

**하지 말 것**:
- 파인더 전용 도수 정의 (RED 5)
- 서버 왕복 (RED 25)
- 파인더 결과 저장 — Phase 1a 범위 밖
