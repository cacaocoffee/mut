## 근거

**`FR-SEARCH-002`** (**P0**): **모든 필터 값 옆에 실시간 결과 개수를 표시하고, 0건인 값은 비활성 처리한다.** **초기부터 넣지 않으면 나중에 UI를 다시 짜야 한다**

**SPEC-05 §5 패싯 카운트를 어디서 세나**

| 단계 | 방식 |
|---|---|
| **Phase 1** | 목록 응답에 전체 코퍼스가 담기므로 **클라이언트에서 계산.** **현재 `facetCounts()`가 하는 일** |
| 확장 후 | `GET /cocktails/facets`가 축별 카운트를 반환 |

> **UI 계약은 두 단계에서 동일하다.** 값 옆에 숫자, 0이면 비활성. **계산 위치만 바뀐다.**

**SPEC-05 §4 필터를 서버로 보내지 않는 이유**

> 필터 결과는 색인 대상이 아니고(`PRIN-P06`), **Phase 1 규모(칵테일 100 · 바 100)에서는 전체 목록을 받아 클라이언트에서 거르는 편이 왕복 없이 즉각적이다.** 데이터가 커지면 서버 필터로 옮기되 **URL 계약은 유지한다.**

**SPEC-05 §4**: `/cocktails/search?…` — **클라이언트 필터**, `noindex`

**`FR-SEARCH-005`**: 필터 조합을 **URL 쿼리스트링에 반영해 공유 가능**하게 하되 **`noindex`**
**`FR-SEARCH-003`**: 도수 **4구간**. **연속 슬라이더를 쓰지 않는다** (ADR-0003)
**`FR-SEARCH-009`**: **조합 불가능한 값이 즉시 0으로 떨어져야 한다**

**`NFR-A-06`**: **비활성 필터 칩은 `disabled` + 개수를 함께 읽어준다** (접근성)
**`NFR-S-02`**: 필터 결과는 `noindex` — 배포 차단
**`NFR-P-01`**: LCP ≤ 2.5s (탐색 화면 — SPEC-04 §1.1)

**INDEX 결합점**: 019(서버 패싯) ← 040. **Phase 1은 클라이언트 계산 유지**, 019는 SSG·확장 대비. **두 구현이 갈라지지 않게 대조 테스트**를 여기서 넣는다 (이슈 019 DoD)

**현재**: `apps/web/components/search-screen.tsx` + `packages/domain/src/search.ts`의 `facetCounts()` — **유지 대상** (SPEC-01 §6)

## GREEN

### 기존 코드 유지 (SPEC-01 §6)

`packages/domain/src/search.ts`의 필터·`facetCounts()`를 **그대로 쓴다.** SPEC-01 §6이 "클라이언트 필터로 유지"라고 명시했다.

바뀌는 것은 **데이터 출처**뿐이다:

```ts
// 지금: import { COCKTAILS } from "@repo/domain"
// 이후: const corpus = await fetch(`${API}/api/v1/cocktails?size=1000`)
```

### 서버·클라이언트 대조 (RED 19·20 — INDEX 결합점)

```ts
// 두 구현이 갈라지면 UI가 거짓말을 한다
test("facetCounts가 서버 /facets 와 일치", async () => {
  for (const filter of SAMPLE_FILTERS) {
    expect(facetCounts(corpus, filter)).toEqual(await fetchFacets(filter));
  }
});
```

**이 테스트가 이슈 019의 존재 이유를 지킨다.** 없으면 두 계산이 조용히 갈라진다.

### 패싯 UI 계약 (SPEC-05 §5)

> **UI 계약은 두 단계에서 동일하다.** 값 옆에 숫자, 0이면 비활성. **계산 위치만 바뀐다.**

컴포넌트가 `counts: Record<string, number>` 를 받게 두면, 나중에 서버 응답으로 갈아끼울 때 **컴포넌트를 고치지 않는다.**

### 전체 코퍼스 로딩 (RED 37, SPEC-05 §4)

Phase 1 규모(500종)라 한 번에 받는다. **필터마다 서버 왕복하지 않는다** — 그게 SPEC-05 §4가 클라이언트 필터를 고른 이유다.

**결정** 500종 × 상세 필드면 응답이 크다. **목록 응답은 필터에 필요한 필드만** 담아야 한다 (이슈 018의 `CocktailListItem`). GAPS 등재.

**하지 말 것**:
- `search.ts` 재작성 — 유지 대상
- 서버 필터로 전환 — SPEC-05 §4가 "데이터가 커지면"이라 했다
- 통합 검색 — 이슈 042
- 파인더 — 이슈 041
