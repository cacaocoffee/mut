### 1.9 검색

| 항목 | 결정 |
|---|---|
| 비한글 문자열의 초성 | **빈 문자열** — `Negroni`는 `name_en` 매칭으로 잡힌다 |
| 초성 혼합 입력(`마ㄹㄱ`) | **일반 검색으로 처리** |
| 띄어쓰기 변형 | **정규화 매칭 + 에디터 별칭 양쪽** |
| 빈 그룹 | **빈 배열로 포함** — 클라이언트가 자리를 알아야 한다 |
| 그룹 순서 | `cocktail` → `ingredient` → `bar`(1b) → `article`(2) |
| 빈 `q` | **400** |
| 검색 가중치 | `entity_type` 별 고정값으로 시작 (G-13 미정) |
| 회수·보관·미승인 엔티티의 색인 행 | **지우지 않고 `is_published = false`** (§3 → §1, 이슈 017) |
| 초성 컬럼에 담는 것 | **이름 + 별칭**을 각각 분해해 공백으로 잇는다. 중복은 한 번만 (이슈 017) |

`is_published` 로 내리는 이유: 행을 지우면 **회수 상태에서 고친 이름이 색인에 반영되지 않아**
다시 발행하는 순간 낡은 이름으로 검색된다. 공개 노출은 조회 쪽이 이 플래그로 거른다 (이슈 024).
`IngredientSaved` 주석의 "미승인 재료는 색인하지 않는다" 도 같은 방식으로 지킨다.

### 1.12 이미지 저장 (D-6 해결, 2026-08-12)

**리포지토리에 직접 넣는다.** `apps/web/public/cocktails/{slug}.webp`

| 무엇 | 결정 |
|---|---|
| 저장 위치 | 리포지토리 (`apps/web/public/cocktails/`) |
| 파일명 | `{slug}.webp` — 슬러그가 불변(`PRIN-D02`)이라 파일명도 불변이다 |
| 출처 | **에디터 본인이 찍은 사진만** (`PRIN-P03` 과 같은 취지 — 남의 사진을 옮기지 않는다) |
| 업로드 경로 | **만들지 않는다.** 파일을 커밋한다 — 어드민 업로드는 Phase 2 |
| OG 이미지 | 같은 파일을 쓴다. 별도 렌더링 파이프라인을 두지 않는다 |

**근거**: 외부 의존이 0 이고 Next `Image` 최적화와 SSG 에 그대로 얹힌다. CDN URL 참조는
호스트가 Referer 로 막거나 원본이 사라지면 이미지가 깨지는데, **그 시점을 우리가 알 수 없다.**

**대가**: 리포 용량이 는다. 20장이면 수 MB 다.

> ⚠️ **이건 Phase 1a 한시 조치다.** 최종 형태는 **칵테일 레코드가 자기 이미지를 들고 있는 것**
> (`cocktail.image_*` 또는 별도 `cocktail_image` 테이블 + 오브젝트 스토리지)이고, 에디터가
> 어드민에서 올린다. 지금 파일을 커밋하는 이유는 **시드 24→40종을 먼저 채우기 위해서**지
> 이 방식이 옳아서가 아니다.
>
> 그래서 지금 파일명을 `{slug}.webp` 로 고정한다 — 슬러그가 불변이라(`PRIN-D02`)
> 나중에 레코드로 옮길 때 **매핑이 자동으로 성립한다.** 임의 파일명을 쓰면 그때 사람이 짝을 맞춰야 한다.

### 1.13 배치 실행 방식 (§3 → §1, 2026-08-12)

**Spring Batch 를 지금 쓰지 않는다.** `@Scheduled` + 트랜잭션 하나로 간다 (이슈 016).

SPEC-05 §8 이 Spring Batch 를 지정했지만, §3 이 이 항목의 판단 시점을 **"1b 에 배치가 3종 늘 때"**
로 잡아 뒀고 지금은 배치가 하나다. 지금 도입하면 메타 테이블 6개와 시퀀스 3개가 들어오는데,
그것들은 SPEC-06 §1.2 의 공통 컬럼 규약도 §6 의 명명 규칙도 따르지 않아 `SchemaLint` 예외를
그만큼 뚫어야 한다 — **규칙에 구멍을 내는 비용이 얻는 것보다 크다.**

**재검토 시점**: Phase 1b (바 검증 · 파트너 집계 · 인스타 동기화가 붙을 때).
