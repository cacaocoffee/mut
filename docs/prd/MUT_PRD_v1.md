## 00. 전제 및 가정

아래가 흔들리면 하위 섹션도 함께 흔들린다. 변경 시 이 표부터 고친다.

| 구분 | 가정 |
|---|---|
| 플랫폼 | 반응형 웹 우선 → 이후 앱. 콘텐츠 SEO가 초기 유입의 핵심이라 웹을 선행한다 |
| 수익 모델 | 제휴사 구독형 입점료 + 브랜디드 콘텐츠. 주류 직접 판매 없음 |
| 초기 커버리지 | 서울 (강남·이태원·을지로·성수·청담) → 부산·제주 확장 |
| 콘텐츠 소스 | 자체 에디토리얼 + 제휴 바 제공 + 유저 저장 데이터. UGC 리뷰는 v2 |
| 팀 규모 | 개발 1~2, 에디터 1, 영업 1 수준의 소규모 |

## 01. 배경과 문제

### 1.1 시장 상황

- 하이볼·위스키 붐 이후 홈텐딩 인구가 급증했으나, 국내 사용자가 참고하는 레시피는 개인 블로그·유튜브·릴스에 흩어져 있다
- 바 정보는 사실상 인스타그램 해시태그와 블로그 리뷰가 전부다. 시그니처 메뉴, 바텐더, 스타일, 예약 방식 같은 구조화 데이터가 없다
- 해외에는 Difford's Guide(6,000+ 칵테일 DB), Punch(2,500+ 레시피 + 에디토리얼), World's 50 Best Bars(랭킹)가 각 축을 담당한다. 국내에 대응 서비스가 없다
- 아시아 50 베스트 바에 서울 소재 바가 지속 진입 중이다. 국내 신에 대한 외부 관심은 이미 있고, 담을 그릇이 없을 뿐이다

### 1.2 핵심 문제

| 사용자 | 문제 |
|---|---|
| 홈텐더 | 레시피의 신뢰도를 판단할 수 없다. 국내에서 구할 수 있는 재료인지 모른다 |
| 바 탐색 유저 | 인스타 사진만으로는 그 바가 어떤 곳인지 알 수 없다. 분위기, 강점, 가격대, 웨이팅 |
| 바 사업자 | 알릴 채널이 인스타밖에 없다. 광고비 대비 유입을 측정할 수 없다 |

### 1.3 가설

> 칵테일 레시피 DB와 바 DB를 하나의 그래프로 연결하면, 각각을 따로 하는 것보다 강력하다.

칵테일 상세에서 `이 칵테일을 잘 만드는 서울의 바`로, 바 상세에서 `이 바의 시그니처 레시피`로 이어지는 순환이 해자다. 레퍼런스 네 곳 중 어디도 이 연결을 구현하지 않았다. Difford's는 DB, Punch는 에디토리얼, 50 Best는 랭킹으로 각자 따로 논다.

## 02. 목표와 지표

### 2.1 제품 목표

1. **국내 최대의 구조화된 칵테일 레시피 DB** — 국내 구매 가능한 재료 기준으로 정규화
2. **신뢰할 수 있는 바 큐레이션** — 리뷰 총점이 아닌 에디토리얼 관점
3. **제휴사에 측정 가능한 송객 가치** — 광고가 아닌 콘텐츠 형태로

### 2.2 성공 지표

| 구분 | 지표 | 6개월 목표 |
|---|---|---|
| 콘텐츠 | 등록 칵테일 수 | 500 |
| 콘텐츠 | 등록 바 수 (서울) | 300 |
| 트래픽 | MAU | 30,000 |
| 트래픽 | 유기 검색 유입 비중 | 50% 이상 |
| 인게이지먼트 | 칵테일↔바 크로스 이동률 | 세션의 20% |
| 인게이지먼트 | ~~내 술장 재료 3개 이상 등록 유저~~ — 폐기, 대체 지표는 [G-50](./GAPS.md) | ~~가입자의 25%~~ |
| 비즈니스 | 유료 제휴사 수 | 30 |
| 비즈니스 | 제휴사 상세 → 외부 액션 CTR | 12% |

트래픽보다 **크로스 이동률**이 진짜 검증 지표다. 그래프 가설이 맞았는지를 그 숫자가 말해준다.

### 2.3 명시적 비목표

- **주류 이커머스** — 국내법상 온라인 주류 판매는 원칙적으로 불가. 픽업 커머스도 v1에서 다루지 않는다
- **예약 시스템 자체 구축** — 캐치테이블·테이블링·네이버 예약으로 딥링크 전달만
- **별점 기반 리뷰 총점** — 의도적으로 배제
- **바텐더 채용·구인** — v3 이후

### 2.4 포지셔닝

| 대상 | 차이점 |
|---|---|
| 네이버 지도 · 다이닝코드 | 평점 집계가 아니라 에디토리얼 큐레이션. 모든 바를 담지 않는다 |
| 캐치테이블 | 예약 인프라가 아니라 발견 레이어 |
| 데일리샷 | 술을 팔지 않는다. 지식과 장소를 다룬다 |
| 개인 유튜브·블로그 | 검색과 필터가 가능한 구조화 DB |

## 03. 타깃 사용자

P1과 P2가 유저, P3은 고객이자 유저다. 세 동선이 한 제품 안에서 만나야 한다.

### P1. 홈텐더 — 지훈 (28, 직장인)

- **상황** 셰이커와 지거를 샀고 진·베르무트·비터스 정도는 갖췄다
- **검색어** 네그로니 비율 / 홈바 필수 리큐르 / 진토닉 맛있게
- **니즈** 믿을 만한 표준 레시피, 지금 가진 재료로 만들 수 있는 것
- **핵심 기능** 레시피 상세, 내 술장 역검색, 메이킹 방법 필터

### P2. 바 탐험가 — 수연 (32, 마케터)

- **상황** 한 달에 2~3회 칵테일 바 방문. 새로운 곳을 계속 찾는다
- **검색어** 을지로 칵테일 바 / 데이트 위스키바 강남 / 서울 스피크이지
- **니즈** 사진으로는 알 수 없는 그 바의 성격과 강점, 예약 필요 여부
- **핵심 기능** 바 탐색 필터, 큐레이션 리스트, 시그니처 메뉴

### P3. 제휴 바 오너 (사업자)

- **상황** 인스타 운영에 지쳤고 광고비 효과를 모른다
- **니즈** 제대로 취재된 소개 콘텐츠와 유입 데이터
- **핵심 기능** 파트너 상세, 파트너 대시보드

## 05. 분류 체계

> **카테고리와 필터는 다른 것이다.** 이 구분이 무너지면 URL 구조와 SEO가 함께 무너진다.
>
> **카테고리** — 모든 칵테일이 반드시 하나씩 갖는 고정 분류. URL이 되고, 랜딩 페이지가 되고, 색인 대상이 된다. 기주·스타일·메이킹 방법 3축.
>
> **필터** — 탐색을 돕는 도구. URL 쿼리스트링으로만 존재하고 색인하지 않는다. 당도·도수·향과 맛·보유 재료.
>
> 당도나 도수를 카테고리로 올리면 `/cocktails/sweet/high-abv/gin/` 같은 조합 폭발이 생기고 중복 콘텐츠로 SEO 페널티를 받는다.

### 5.1 축 1 — 기주 (Base)

단일값, 필수. 복수 허용하면 마티니가 진과 베르무트 양쪽에 걸려 필터가 무너진다.

| 값 | 슬러그 | 비고 |
|---|---|---|
| 진 | `gin` | |
| 보드카 | `vodka` | |
| 럼 | `rum` | |
| 데킬라 · 메즈칼 | `agave` | |
| 위스키 | `whisky` | 버번 · 스카치 · 재패니즈는 하위 태그 |
| 브랜디 | `brandy` | 코냑 · 칼바도스 · 피스코 포함 |
| 리큐르 | `liqueur` | 아마로 · 캄파리가 주인공인 것 |
| 와인 · 스파클링 | `wine` | 스프리츠 · 미모사 · 벨리니 |
| 전통주 | `korean` | 국내판 정체성 축. 소주 · 막걸리 · 문배주 등 |
| 무알콜 | `non-alcoholic` | |

정본은 `packages/domain/src/types.ts`의 `BaseSpirit` · `BASE_SLUGS`다.

### 5.2 축 2 — 스타일 (Style)

레시피 **구조** 기준으로 정의한다. 클래식·모던 같은 시대 구분으로 잡으면 필터로서 쓸모가 없다. 복수 허용하되 primary 하나를 반드시 지정한다.

| 값 | 슬러그 | 대표 |
|---|---|---|
| 하이볼 · 롱드링크 | `highball` | 진토닉, 모스코뮬, 콜린스 |
| 사워 | `sour` | 위스키 사워, 다이키리, 마르가리타, 김렛 |
| 스피릿 포워드 | `spirit-forward` | 마티니, 올드패션드, 네그로니, 맨해튼 |
| 스프리츠 · 스파클링 | `spritz` | 아페롤 스프리츠, 프렌치 75 |
| 트로피컬 · 티키 | `tiki` | 마이타이, 피나콜라다, 좀비 |
| 크리미 · 디저트 | `creamy` | 화이트 러시안, 에스프레소 마티니 |
| 핫 드링크 | `hot` | 아이리시 커피, 핫 토디 |
| 프로즌 | `frozen` | 프로즌 마르가리타 |
| 샷 | `shot` | B-52, 테킬라 슬래머 |

### 5.3 축 3 — 메이킹 방법 (Method)

단일값, 필수. 이 축의 실질 가치는 **난이도 프록시**다. 빌드만 켜면 도구 없는 초보가 오늘 만들 수 있는 것만 남는다.

| 값 | 슬러그 | 필요 도구 | 예상 비중 |
|---|---|---|---|
| 빌드 | `build` | 잔, 바스푼 | 30% |
| 셰이크 | `shake` | 셰이커 | 40% |
| 스터 | `stir` | 믹싱글라스 | 20% |
| 블렌드 | `blend` | 블렌더 | 5% |
| 기타 | `etc` | 스로잉 · 머들링 · 인퓨징 · 직화 | 5% |

### 5.4 요구사항

| ID | 내용 |
|---|---|
| **R-C-1** | 세 축은 모든 칵테일에 필수값이다. NULL을 허용하면 카테고리 페이지에서 누락이 생기고, 그 자리가 곧 검색 유입 손실이다 |
| R-C-2 | 카테고리 URL은 `/cocktails/base/gin/`, `/cocktails/style/sour/`, `/cocktails/method/build/` 형태의 단일 축 경로만 색인한다. 축 조합 경로는 만들지 않는다 |
| R-C-3 | 배리에이션 추천은 `style_primary` 일치를 1순위, 기주 일치를 2순위로 계산한다 |

## 06. F1 · 칵테일 정보

상세 페이지의 완성도가 곧 SEO 경쟁력이다. 여기에 가장 많은 시간을 쓴다.

### 6.1 상세 페이지 구성

| 블록 | 내용 | 필수 |
|---|---|---|
| 히어로 | 대표 이미지, 한글명 · 영문명, 한 줄 요약 | 필수 |
| 분류 | 기주 · 스타일 · 메이킹 방법 (각 카테고리 페이지로 링크) | 필수 |
| 스펙 | 도수, 당도, 소요시간, 글라스 | 필수 |
| 재료 | 재료명 + 용량. ml / oz / 대시 / 바스푼 토글 | 필수 |

| 국내 구매 가이드 | 재료별 유통 여부 · 대체재 · 가격대 | 필수 |

| 액션 | 저장, 공유, 내 술장 재료 대조 | 필수 |

### 6.2 요구사항

| ID | 내용 |
|---|---|
| **R-F1.1-1** | 레시피는 프리텍스트가 아니라 구조화 필드로 저장한다. 재료는 문자열이 아니라 재료 마스터 테이블 참조여야 한다. 이게 안 되면 역검색과 바 연결이 전부 불가능하다 |

| R-F1.1-4 | 도수는 재료의 도수 · 용량과 기법별 희석률(셰이크 25%, 스터 20%, 빌드 10%)로 자동 계산하고, 수동 오버라이드 필드를 둔다 |

### 설계 노트

- **`counts_for_stock`** — 가니시 · 얼음 · 물을 역검색 판정에서 빼기 위한 플래그다. 이게 없으면 민트 잎 하나 없다고 모히토가 안 나온다.
- **Cocktail과 Recipe의 분리** — 하나의 칵테일에 표준 버전과 여러 바의 버전이 공존해야 하고, 이게 파트너 상품의 핵심이다. 나중에 분리하면 마이그레이션 비용이 크다.
- **`style_primary`** — 배리에이션 추천의 유일한 기준. NULL이면 추천이 태그 매칭으로 퇴화한다.
- **`domestic_availability`** — 이 서비스의 국내판 정체성을 만드는 필드다.

## 13. 콘텐츠 운영 원칙

1. **레시피는 출처를 밝힌다.** 고전 칵테일은 원전(Savoy Cocktail Book, IBA 공식 스펙)과의 차이를 명시하고, 창작 레시피는 창작자를 표기한다.
2. **표준 레시피는 반드시 만들어보고 발행한다.** 검증 없는 레시피가 하나만 돌아도 신뢰가 무너진다.
3. **향과 맛은 만들어본 사람이 쓴다.** 다른 사이트 설명을 옮기면 이 서비스의 존재 이유가 사라진다.
4. **광고와 콘텐츠를 시각적으로 구분한다.** 제휴 콘텐츠 라벨을 축소하거나 흐리게 처리하지 않는다.
5. **부정적 평가는 싣지 않되 칭찬도 하지 않는다.** 큐레이션에서 제외하는 것으로 의견을 표현한다. 소규모 자영업자를 다루는 서비스에서 공개 비판은 리스크 대비 실익이 없다.
6. **바 정보는 분기 1회 검증한다.** 폐업 · 이전이 잦은 업종이다.

|---|---|---|

## 17. 기술 스택

v1.0에는 이 절이 없었다. 12장이 "SSR 또는 SSG 필수", "정적 생성 후 ISR", "CMS 필수"라고
요구 수준만 적었고 무엇으로 만드는지는 비어 있었다.

### 확정

| 층 | 선택 | 근거 |
|---|---|---|
| 프레임워크 | **Next.js 16 (App Router)** | 12장의 SSG + ISR 요구를 그대로 만족. 칵테일·바 상세를 정적 생성 |
| 언어 | **TypeScript** (strict) | 분류 3축이 enum이라 타입이 곧 `R-C-1` 강제 수단 |
| 저장소 | **npm workspaces 모노레포** | `apps/web` · `packages/domain` · `packages/ui` |
| 스타일 | **순수 CSS + 토큰** | 시안이 플레인 CSS 디자인 시스템이라 변환 손실이 없다 |
| 데이터 무결성 | **`packages/domain/src/validate.ts`** | `R-C-1` `R-C-3` `R-F1.2-1`을 빌드에서 강제 |

경계는 이렇게 나눈다. **`packages/domain`은 프레임워크에 의존하지 않는다** — 나중에 어드민이나
배치 작업이 같은 분류 로직을 써야 하기 때문이다.

### 미정 — Phase 1 착수 전 필요

| 항목 | 막고 있는 것 | 비고 |
|---|---|---|
| **DB** | [G-14](./GAPS.md#g-14) API 계약 | 현재는 정적 TS 배열 24종. 11장 스키마를 얹을 대상이 필요하다 |
| **CMS** | [G-15](./GAPS.md#g-15) 어드민 명세 | `R-F1.1-2`(향과 맛 미입력 시 발행 불가)를 강제할 지점이 여기다 |
| **검색 인프라** | [G-13](./GAPS.md#g-13) | `R-F2.1-4` 초성 검색은 DB `LIKE`로 안 된다. 별도 색인이나 검색엔진이 필요 |
| **호스팅 / 배포** | — | ISR을 지원해야 한다 |

### 현재 구현 범위

프로토타입이다. 24종이 정적 배열에 있고, 바 도메인(F3) · 제휴(F4) · 로그인(F5) · 어드민은 없다.
탐색 · 상세 · 파인더 3개 화면이 시안대로 동작하며 분류 3축과 필터 패싯 카운트를 검증한다.

# 부록 A. 디자인 시스템 — 폐기됨

이 부록은 시안을 열람하지 못한 상태에서 쓴 **제안안**이었고, 확보된 시안(Modernist)과
색 · 서체 · 라운드 · elevation · 스페이싱이 전부 달랐다. 당도 스케일도 3단으로 적혀 있어
[ADR-0002](../decisions/ADR-0002-taxonomy.md)의 4단계와 어긋났다.

혼동을 막기 위해 **본문을 삭제했다.** 복붙 사고를 막는 것이 기록 보존보다 중요하다.

| 찾는 것 | 어디 |
|---|---|
| **토큰 정본** (색 · 서체 · 간격 · 라운드 · 그림자) | `packages/ui/styles.css` |
| 사용 규칙 · 컴포넌트 목록 | [`docs/design/`](../design/) |
| 시안 원본 | `docs/design/source/` |
| 화면별 구성 (계량 표기 · 필터 칩 · 상세 블록) | [`docs/screens/`](../screens/) |
| **폐기 경위와 대조표** | [ADR-0001](../decisions/ADR-0001-design-system.md) |
