- **심각도 A**는 지금 구현을 막거나 이미 어긋나 있는 것. B는 Phase 1 착수 전 필요. C는 그 이후.

## A등급 — 해결됨 (기록)

### G-01

**당도 단계 수 충돌**

| 출처 | 값 |
|---|---|
| PRD `R-F1.1-5` (267줄) | 3단계 — 드라이 · 미디엄 · 스위트 |
| PRD 데이터 모델 (457줄) | `sweetness enum dry \| medium \| sweet` |
| 시안 · 현재 코드 | 4단계 — 드라이 · 세미 드라이 · 세미 스위트 · 스위트 |

현재 `packages/domain/src/types.ts`의 `SweetLevel`은 `0|1|2|3`이고, 24개 항목이 전부 4단계로 색인돼 있다.
파인더 점수 계산(`matchScore`)도 4단계 전제로 `sweet === 1 ? 1.5 : sweet` 같은 보정을 쓴다.

> **제안: 4단계 유지.** 3단계로 줄이면 시안의 당도 태그 색 스케일(중립 → accent-2 → accent-200 → accent 채움)이
> 4칸 전제라 다시 디자인해야 하고, 24개 항목의 재색인이 필요하다. 무엇보다 "세미 드라이"와 "세미 스위트"를
> 하나로 합치면 네그로니(0)와 김렛(1)이 같은 칸에 들어가는데, 이 둘은 실제로 다른 음료다.
> PRD 쪽을 4단계로 고치는 편이 싸다.

**차단 대상** — 데이터 모델 확정, 필터 UI, 파인더 점수식.

### G-02

**향·맛 태그 집합 충돌**

| PRD 6.3 (9개) | 시안 · 코드 (7개) |
|---|---|
| 시트러스 | `citrus` ✅ |
| 프루티 | `fruity` ✅ |
| 허브 | `herbal` ✅ |
| 스파이시 | `spicy` ✅ |
| 스모키 | `smoky` ✅ |
| 비터 | `bitter` ✅ |
| 플로럴 | — **없음** |
| 너티 · 로스티 | — **없음** |
| 크리미 | — **없음** |
| — | `sour` **시안에만 있음** |

PRD는 산미를 시트러스 안에 넣었다("레몬·라임·자몽 계열의 산미"). 시안은 `citrus`(향)와 `sour`(맛)를 분리했다.
현재 코드의 `matchScore`는 이 분리를 전제로 `citrus`를 고르면 `sour`에 부분 점수(+14)를 준다.

> **제안: 시안 7개 + PRD 3개 = 9개로 합집합.** `sour`를 살리고 `플로럴 / 너티·로스티 / 크리미`를 추가한다.
> 근거는 두 가지다. (1) `sour`와 `citrus`는 실제로 다른 축이다 — 위스키 사워는 `sour`지만 시트러스 향이 주인공이 아니다.
> (2) 빠진 3개는 커버리지 문제다. 에스프레소 마티니에 `너티·로스티`가 없으면 "커피 향" 검색이 불가능하고,
> 24종을 500종으로 늘리면 플로럴(엘더플라워·바이올렛) 계열이 반드시 들어온다.
>
> 단, `R-F1.2-1`의 **최대 3개 제한**은 유지한다. 현재 데이터는 최대 3개라 그대로 통과한다.

**차단 대상** — 필터 UI, 파인더 3번 질문, 500종 확장 시 재색인 비용.

### G-03

**스타일 축이 데이터에 없음 — `R-C-1` 위반**

PRD 5장은 카테고리를 3축(기주 · 스타일 · 메이킹 방법)으로 정의하고, `R-C-1`에서
"세 축은 모든 칵테일에 필수값이다. NULL을 허용하면 카테고리 페이지에서 누락이 생긴다"고 못박았다.
`R-C-3`의 배리에이션 추천도 `style_primary` 일치를 1순위로 쓴다.

그런데 시안에도, 현재 `packages/domain/src/data.ts`에도 **스타일 필드가 없다.**
현재 상세 화면의 "같은 기주 RELATED"는 기주만으로 추천하는데, 이건 `R-C-3`가 명시적으로
"NULL이면 추천이 태그 매칭으로 퇴화한다"고 경고한 바로 그 상태다.

> **제안: `style[]` + `stylePrimary` 필드를 추가하고 24종을 색인한다.** PRD 5.2의 9종 중 현재 데이터가
> 실제로 쓰는 것은 6종(`highball` `sour` `spirit-forward` `tiki` `creamy` — `spritz` `hot` `frozen` `shot`은 해당 없음)이다.
> 24개 색인은 한 번에 끝나고, 이걸 미루면 500종 시점에 전수 재색인이 된다.
>
> 색인 초안(제안):
>
> | 스타일 | 해당 항목 |
> |---|---|
> | `spirit-forward` | 네그로니 · 마티니 · 올드패션드 · 맨해튼 · 불바디에 · 문배 올드패션드 |
> | `sour` | 김렛 · 사우스사이드 · 코즈모폴리탄 · 위스키 사워 · 페니실린 · 다이키리 · 마르가리타 |
> | `highball` | 진토닉 · 모스코 뮬 · 블러디 메리 · 모히토 · 다크 앤 스토미 · 팔로마 · 소주 하이볼 · 시트러스 슈럽 |
> | `tiki` | 마이 타이 |
> | `creamy` | 에스프레소 마티니 · 막걸리 콜라다 |

**차단 대상** — 카테고리 URL(`/cocktails/style/sour/`), 배리에이션 추천, SEO 랜딩 페이지.

### G-05

**부록 A가 시안과 다름 — 문서 스스로 폐기를 예고함**

부록 A는 첫 줄에 이렇게 적혀 있다(622–624줄):

> 시안 파일을 받으면 팔레트와 타이포를 그쪽 기준으로 교체한다.

시안은 확보됐다(`docs/design/source/`). 실제 값은 정반대에 가깝다.

> **제안: 부록 A.1 · A.2 · A.6을 폐기하고 Modernist로 교체.** 문서가 지시한 대로다.

### G-06

**다크 모드 충돌 — 남은 진짜 결정**

G-05를 "시안 우선"으로 정리해도 이건 안 풀린다. NFR(541줄)이 별도로 요구한다:

> 접근성 — 명도 대비 WCAG AA. **다크 모드가 기본 테마**

그런데 Modernist에는 다크 테마가 **정의돼 있지 않다.** `styles.css`의 램프는 라이트 그라운드
한 벌뿐이고, 시안 readme는 "a near-mono red on white"를 시스템의 정체성으로 규정한다.

선택지는 셋이고, 이건 제품 결정이라 제가 정하지 않았다.

| 안 | 내용 | 비용 |
|---|---|---|
| **가** | 라이트 단일. NFR의 "다크 기본"을 삭제 | 없음. 지금 상태 그대로 |
| **나** | 다크를 Modernist 규칙으로 파생 (accent를 `--color-accent-500`로 올리고 램프 반전) | 램프 재생성 + 전 컴포넌트 대비 재검증 |
| **다** | 라이트 기본 + 다크 옵션 | 나 + 토글·저장 |

> **제안: 가(라이트 단일), 단 근거를 남길 것.** "바는 어두우니 다크"는 부록 A의 논리였고,
> 그 부록은 시안 없이 쓰였다. 시안이 라이트를 골랐고 이미 구현·검증됐다.
> 다크가 정말 필요하다는 근거(사용자 조사·야간 사용 비중)가 나오면 그때 **나**로 간다.

**차단 대상** — `packages/ui` 토큰 확장 여부. 결정 전엔 다크 관련 코드를 쓰지 않는다.

### G-07

**기술 스택이 PRD에 없음**

PRD 768줄 어디에도 프레임워크 · DB · 호스팅 언급이 없다. NFR 12장이 "SSR 또는 SSG 필수",
"정적 생성 후 ISR", "어드민 CMS 필수"라고 요구 수준만 적었다.

현재 코드가 이미 고른 것:

| 층 | 선택 | 근거 |
|---|---|---|
| 프레임워크 | Next.js 16 (App Router) | NFR SSG + ISR 요구를 그대로 만족 |
| 언어 | TypeScript strict | — |
| 구조 | npm workspaces 모노레포 | `apps/web` · `packages/domain` · `packages/ui` |
| 스타일 | 순수 CSS + 토큰 | 시안이 플레인 CSS 디자인 시스템 |
| 데이터 | **없음 — 정적 TS 배열 24개** | 프로토타입 단계 |
| 호스팅 | 미정 | — |
| CMS | 미정 | NFR이 요구하나 후보 없음 |

> **제안:** 확정된 것은 PRD에 적어 굳히고, 미정 3건(DB · 호스팅 · CMS)은 16장 결정 목록에 올린다.
> 특히 **DB와 CMS는 G-14(API 계약)·G-15(어드민)를 막고 있어** Phase 1 착수 전 필수다.

**진행 (2026-08-06)** — DB(PostgreSQL 16) · CMS(자체 어드민) · 백엔드(Kotlin + Spring)가 확정됐고
[SPEC-05](../spec/SPEC-05_아키텍처.md) · [SPEC-06](../spec/SPEC-06_데이터모델_ERD.md) ·
[SPEC-07](../spec/SPEC-07_API명세.md)에 반영했다.

**남은 미정 2건**

| 항목 | 막고 있는 것 |
|---|---|
| **호스팅 · 배포** | 배포 파이프라인. **추가 제약** — httpOnly 쿠키 세션이라 프론트와 API가 같은 상위 도메인이어야 한다 ([SPEC-07 §1.2](../spec/SPEC-07_API명세.md)) |

**진행 (2026-08-20)** — 둘 다 [ADR-0007](../decisions/ADR-0007-hosting.md)로 정했다.

| 층 | 어디 | 1단계에 쓰나 |
|---|---|---|
| 웹 | Vercel (Hobby $0) | **쓴다** |

**SPEC-06이 불리언 명명에서 스스로와 충돌한다** *(더 구체적인 쪽을 따랐다)*

### G-24

**`INV-INGREDIENT-01`을 SPEC-06 §4.3은 "앱 강제"로 분류했지만 DB로도 강제한다** *(더 강한 방향)*

[SPEC-06 §4.3](../spec/SPEC-06_데이터모델_ERD.md)이 `INV-INGREDIENT-01`·`02`를
"조건부라 DB 제약으로 표현 불가"로 분류했다. `01`은 **표현 가능하다.**

```sql
CONSTRAINT ck_ingredient__substitute CHECK (
    domestic_availability NOT IN ('import_only','unavailable')
    OR (substitute_note IS NOT NULL AND substitute_note ~ '\S')
)
```

같은 문서 §4 서두가 **"DB로 강제할 수 있는 것은 DB에서 한다"**고 했으므로 §4.3의 분류보다
서두의 원칙이 우선한다고 보고 **양쪽 다** 걸었다 (`PRIN-T05`).

| 어디서 | 왜 |
|---|---|
| 앱 (`Ingredient.validate`) | 에디터에게 **어느 항목이 왜** 막혔는지 알려 준다. DB 제약 위반은 `violations`를 못 만든다 (`FR-ADMIN-003`) |
| DB (`CHECK`) | 배치·마이그레이션은 앱을 거치지 않는다 |

**해결 (2026-08-11)** — 이슈 008이 양쪽에 걸었다. 문서를 고치지 않은 이유는
**규칙이 더 강해진 방향**이라 스펙 위반이 아니기 때문이다. ADR까지는 만들지 않았다.

> ⚠️ **`INV-INGREDIENT-02`(브랜드 광고성 표기)는 여전히 앱 강제다.** "특정 브랜드 언급"의
> 판정이 데이터가 아니라 편집 판단이라 CHECK로 옮길 수 없다. `is_sponsored`가 `NOT NULL`인 것까지가
> DB가 할 수 있는 전부다.

구현 중 두 가지를 잡았다.

- **`trim()`은 공백만 지운다.** 탭·개행으로 채운 값이 통과했다. 코틀린 `isNullOrBlank()`는
  둘 다 잡으므로 앱이 DB보다 엄격해질 뻔했다 → `~ '\S'`로 바꿨다
- **`NULL ~ '\S'`는 `NULL`이고 CHECK는 `NULL`을 통과로 친다.** 안내를 아예 안 적은 경우가
  새어 나갔다 → `IS NOT NULL`을 명시했다 (3값 논리)

### G-26

**`audit_log`가 SPEC-06 §3.8·§4.1을 세 군데서 넘어선다** *(전부 더 강한 방향)*

이슈 014가 감사 로그를 만들며 문서 밖으로 나간 지점이다. 셋 다 `PRIN-T08`의

|---|---|---|---|
| 1 | §3.8 `action` 5종 | **8종** | SPEC-02 §8.1의 전이는 넷인데 표는 `publish`·`unpublish` 둘뿐이다. `archive`·`restore`를 넣지 않으면 전이의 절반이 기록되지 않는다 |

"내렸다"와 "다시 꺼냈다"는 뜻이 다르다. 한 값으로 합치면 재구성(`NFR-O-05`)이 뭉개진다.

> `ApiExceptionHandler`가 `DomainViolationException`을 항상 `422`로 내보내 **그 값이 쓰이지 않는다.**
> 이슈 014의 RED 2가 요구한 것도 `422`라 지금 동작은 맞다. 다만 enum이 들고 있는 상태값이

**이슈 023 의 "1안: `CocktailFacade` 경유 — 경계 준수" 는 틀렸다** *(경계 테스트가 잡았다)*

이슈 023(재료 사전)이 "이 재료를 쓰는 칵테일"(`R-F1.3-1`)의 모듈 경계를 두고 두 안을 적고 1안을 택했다.

**순환이 있다.** [SPEC-05 §3](../spec/SPEC-05_아키텍처.md) 방향표에 `COCKTAIL ──uses──▶ INGREDIENT` 가 이미 있어, `ingredient → cocktail` 은 되돌아오는 화살표다.

놓친 구분이 이것이다 — **Facade 를 거치면 `repository` 직행만 막힌다. 모듈 간 화살표는 그대로 반대다.** `ModuleBoundaryTest` 의 `RED6`(방향표 위반)·`RED7`(순환)이 둘 다 걸렸다.

**교훈**: 이슈 본문의 경계 판단은 방향표를 다시 대조해야 한다. 이 건은 사람이 리뷰로 잡으려면 SPEC-05 §3 을 외우고 있어야 했고, 경계 테스트가 자동으로 잡았다.

### G-30

**SPEC-05 §3 방향표에 `USER ──reads──▶ COCKTAIL` 을 추가했다** *(이슈 031)*

북마크는 [SPEC-05 §3](../spec/SPEC-05_아키텍처.md)이 `USER`에 배정한 것인데(`USER ──owns──▶ STOCK · Bookmark`), 표에는 `USER`가 `COCKTAIL`을 읽을 화살표가 없었다. 그런데 북마크는 본질적으로 **콘텐츠를 가리킨다**:

| 시점 | 왜 대상을 읽어야 하나 | RED |
|---|---|---|
| 저장 | 발행된 것만 저장한다 — `draft`를 저장할 수 있으면 슬러그를 찔러 보는 것만으로 발행 전 콘텐츠의 존재가 샌다 | 5 · 28 |
| 조회 | 무엇을 저장했는지 보여준다 + 사라진 것을 거른다 | 25 · 26 · 27 |

**가리키는 대상을 못 읽는 북마크는 쓸모가 없다.**

**검토했다 버린 안** — `SEARCH` 경유. `SEARCH ──reads──▶ COCKTAIL`이 이미 있지만 그쪽은 `USER`를 읽지 못한다(표에 없다). 북마크 행을 읽으려면 반대 화살표가 필요해져 **문제가 옮겨갈 뿐**이다.

**해결 (2026-08-13)** — 코드가 아니라 **SPEC-05 §3을 먼저 고쳤다** (SPEC-00 §4 · `ModuleBoundaryTest`의 KDoc이 명시한 순서). 순환은 생기지 않는다 — `COCKTAIL`은 `USER`를 참조하지 않는다. `user`의 팬아웃은 `stock` + `cocktail` = 2로 표의 상한(CONTENT의 2) 안이다.

> **[G-28](#g-28)에서 배운 것이 여기서 값을 했다.** 이슈 031 본문의 GREEN도 "`CocktailFacade` 경유 (모듈 경계)"라고 적어, 023과 **똑같은 오해**를 하고 있었다 — Facade를 거치면 `repository` 직행만 막히고 **모듈 화살표는 그대로 반대**다. 023 때는 경계 테스트가 잡았고, 이번엔 착수 전에 알아봤다.

**덤으로 발견한 결함 — `/me`가 공유 캐시에 올라가고 있었다.** `CacheControlFilter`·`PublicEtagFilter`가 `ApiPaths.isPublicApi`로 판정했는데, 그 함수는 "`/api/v1` 아래이고 `/admin`이 아닌 것"이라 `/me/bookmarks`가 통과했다. `Cache-Control: public, max-age=60`과 ETag가 붙어 나갔고, **중간 캐시가 한 사람의 북마크를 다른 사람에게 줄 수 있다**는 뜻이다. `/auth/csrf`도 같이 걸렸다 — 토큰이 60초 캐시되면 세션 바인딩의 의미가 없다.

"공개 API인가"와 "공유 캐시에 올려도 되는가"는 다른 질문이라 `isPubliclyCacheable`로 나눴다. 인증 경로를 열거하지 않고 접두사(`/me`·`/auth`)로 판정한다 — 열거하면 새 개인 경로가 목록에서 빠진 채 들어오고, **그때 새는 것은 조용하다.** `RestConventionTest`에 회귀를 세웠다.

> 이 결함은 이슈 031이 **`/api/v1` 아래 첫 개인 엔드포인트**라서 드러났다. 그 전까지는 공개 아니면 어드민 둘뿐이었다.

### G-31

**홈(`/`)에 이슈가 없다 — 탐색 화면이 그 자리를 쓰고 있었다** *(이슈 040)*

[SPEC-05 §4](../spec/SPEC-05_아키텍처.md)의 렌더링 표는 두 경로를 나눠 적었다.

| 경로 | 방식 | 색인 |
|---|---|---|
| `/` 홈 | ISR 10분 | ✅ |
| `/cocktails/search?…` | 클라이언트 필터 | ❌ `noindex` |

프로토타입은 탐색 화면을 `/` 에 두고 있었다. 그대로 두면 **색인 대상 경로에 `noindex` 화면**이
있는 셈이고, `NFR-S-02`(필터 결과 `noindex`)가 배포 차단 조건이라 그렇게 둘 수 없다.

이슈 040 이 화면을 `/cocktails/search` 로 옮기고 `/` 는 **임시 이동(307)** 으로 남겼다.
영구 이동이 아닌 것이 중요하다 — 홈이 생기면 그 줄을 지우고 페이지를 놓으면 된다.

이동은 `next.config.ts` 의 `redirects()` 가 한다 (이슈 042 에서 옮겼다). 페이지에서
`redirect()` 를 부르면 `/` 가 정적 페이지로 미리 그려지고 이동이 **브라우저에서** 일어나,
화면이 한 번 그려졌다 사라지는 사이에 실행 중이던 것이 문맥을 잃는다.

**남은 일**: 홈 화면을 만드는 이슈가 [INDEX](../issues/INDEX.md) 어느 웨이브에도 없다.
사이트맵은 `/` 를 색인 대상으로 계속 내보내고 있으므로(이슈 039), 홈이 생기기 전까지
그 항목은 **탐색으로 보내는 주소**다. 홈이 무엇을 담을지는 제품 결정이라 여기 남긴다.

### G-33

**파인더(`/finder`)를 색인할지가 정해져 있지 않았다** *(이슈 041에서 결정)*

[SPEC-05 §4](../spec/SPEC-05_아키텍처.md)의 렌더링 표에 `/finder`가 **없다.** 색인 여부도
`noindex` 여부도 적힌 곳이 없었는데, 이슈 041이 답과 단계를 쿼리스트링에 실으면서
(`FR-SEARCH-005`와 같은 이유 — 공유 가능해야 한다) 조합마다 주소가 생겼다.

| 안 | 대가 |
|---|---|
| 전부 색인 | `?abv=high&sweet=dry&…` 조합이 같은 내용으로 색인된다. `PRIN-P06`이 막으려는 중복 콘텐츠 |
| **`noindex`** | 파인더가 검색에서 사라진다. 기능 소개가 있는 진입 화면이고 사이트맵에도 있다 (이슈 039) |
| **canonical 고정** ← 택함 | 진입 화면은 색인되고 답이 붙은 주소는 `/finder`로 합쳐진다 |

**canonical을 답 없는 `/finder`로 고정했다.** 답이 붙은 주소는 같은 화면의 다른 상태이지
다른 문서가 아니다 — 탐색 필터가 `noindex`인 것과 성격이 다르다. 저쪽은 결과 목록 자체가
색인 가치를 갖지 않지만, 파인더는 **주소와 무관하게 같은 질문 화면**이다.

✅ **해결 (2026-08-19)** — SPEC-05 §4 표에 `/finder` 줄을 넣었다 (이슈 052).
**셸 정적 + 클라이언트 진행 · canonical `/finder`** 로, 이미 그렇게 도는 것을 적은 것이다.
표 밖에 있는 경로가 없어야 `PRIN-T04`("경로마다 렌더링 방식이 정해져 있다")가 검사 가능해진다.

### G-34

**시드로 들어온 41종이 검색 색인에 없다** *(이슈 042 에서 드러남)*

`search_document` 는 **발행 이벤트**를 듣고 채워진다 (`SearchIndexListener` · 이슈 017).
그런데 코퍼스는 SQL 시드(`R__seed_02_cocktail.sql` · 이슈 036)로 들어왔다 — 애플리케이션을
거치지 않으므로 이벤트가 없고, 색인 행도 없다.

실측 (2026-08-18, 로컬):

```
select count(*) from cocktail where status='published';   →  41
select count(*) from search_document;                      →   0
GET /api/v1/search?q=네그로니  →  matchedCount: 0
```

**통합 검색이 발행분 전부를 못 찾는다.** 화면·API·색인 코드는 각각 맞는데 셋을 이어 보면
비어 있는 상태라, 어느 한 이슈의 테스트로는 드러나지 않았다.

**남은 일**: 시드 경로에 색인을 채우는 방법을 정해야 한다. 세 가지가 보인다.

| 안 | 성격 |
|---|---|
| 시드 SQL 이 `search_document` 도 넣는다 | 색인 규칙(초성 분해)이 SQL 에 복제된다 — `Chosung` 이 두 벌이 된다 |
| **재색인 배치·CLI** | 이슈 016 의 검증 배치와 같은 자리. 운영에서도 필요하다 (색인이 깨졌을 때 되살릴 길) |
| 시드를 API 로 넣는다 | 이벤트가 자연히 발생한다. 대신 시드가 앱 기동에 묶인다 |

✅ **해결 (2026-08-19)** — 이슈 053 이 **재색인 배치**를 만들었다 (`SearchReindexBatch` ·
`./gradlew reindexSearch`). 세 안 중 배치를 고른 이유는 운영에도 필요해서다 — 색인은
투영이라 마이그레이션·수동 SQL·장애로 언제든 깨지고, 되살릴 길이 하나는 있어야 한다.

**색인 규칙을 배치가 다시 쓰지 않는다** — `SearchIndexSync` 를 그대로 부른다. 배치가
자기 `INSERT` 를 가지면 초성 분해가 두 벌이 되고, 이벤트로 들어간 행과 배치로 들어간 행이
다르게 검색된다. 그 어긋남은 검색 결과로만 드러나서 아무도 못 찾는다.

소유는 `search`(이슈 017 계열)다. 색인의 모양을 아는 쪽이 되살리는 쪽이어야 한다.

### G-35

**계량 단위 5종 중 `ml` 하나만 쓰이고 있다** *(이슈 043 에서 확인)*

`FR-COCKTAIL-019`·`020` 은 `dash`·`barspoon`·`piece`·`top_up` 을 배수·변환에서 뺀다고 했고
이슈 043 이 그 규칙을 구현했다. 그런데 **지금 데이터에는 그 단위가 한 행도 없다.**
발행 41종을 전수 조회한 결과 `unit` 은 전부 `ml` 이고, 나머지는 `amount_label` 이다.

| 라벨 (16종) | 수 |
|---|---|
| `1조각` · `1조각 (선택)` | 17 |
| `2 dash` · `1~2 dash` · `각 2 dash` · `1 dash (8~10 drops)` | 6 |
| `3~4 barspoon` · `10장` · `8장` · `1줄기` · `림 절반` · `1개` · `반 개 …` · `적당량 …` | 나머지 |

**이슈 043 RED 4 의 모호함(`2 dash` 가 라벨인가 수량인가)은 데이터가 답했다** — 라벨이다.
그래서 규칙대로 배수를 타지 않는다. 다만 그 결과로 **"2 dash × 2잔 = 4 dash" 를 사용자가
볼 수 없다.** 두 잔을 만드는 사람은 비터스를 두 배로 넣어야 하는데 화면은 `2 dash` 그대로다.

**한 건은 분명한 데이터 결함이다** — 위스키 사워의 달걀 흰자가 `amount_label = '15ml'` 다.
`ml` 이면서 라벨이라 배수도 oz 변환도 걸리지 않는다.

**남은 일**: 시드(이슈 036)가 라벨로 밀어 넣은 것 중 **수량+단위로 적을 수 있는 것**을
가릴지 정해야 한다. `1조각`·`림 절반`은 라벨이 맞고, `2 dash`·`3~4 barspoon`·`15ml` 는
`amount`+`unit` 으로 적을 수 있다(`1~2`·`3~4` 는 범위라 다시 정해야 한다).
**화면 이슈에서 데이터를 고치지 않는다** — 규칙은 양쪽(라벨·수량) 모두 구현해 두었으므로
데이터가 바뀌면 그날 바로 동작한다.

**진행 (2026-08-19)** — 이슈 051 의 레시피 편집이 다섯 단위를 **입력할 자리**를 만들었다.
여태 `ml` 뿐이던 이유의 절반이 "어드민에서 넣을 길이 없어 SQL 시드로만 들어왔다" 였다.
데이터를 고치는 것은 여전히 에디터의 판단이다 (D-4).

### G-36

| 안 | 대가 |
|---|---|
| 카드 없이 간다 | 카카오톡에서 링크 한 줄로 나온다. `R-F5-5` 미충족 |

**함께 남는 것** — `NFR-S-05`(리치 결과 테스트)와 `NFR-S-06`(카카오톡 카드 확인)은 **수동
측정**이다. 자동화할 수 없어 릴리즈 체크리스트에 있고(SPEC-04 §9.2 · 이슈 050), 절차는

### G-37

**SPEC-10 의 필터 축 목록에 `method` 가 없다** *(이슈 049)*

[SPEC-10 §4.2](../spec/SPEC-10_계측_이벤트.md) 가 `filter_apply.axis` 를 여섯으로 적었다 —

**기주 · 스타일 · 메이킹 · 당도 · 도수 · 맛/향** 여섯에 키워드까지 일곱이다.
`method`(메이킹)는 [이슈 040](https://github.com/cacaocoffee/mut/issues/42)이
`FR-SEARCH-001` 을 채우며 더한 축이고, SPEC-10 은 그 전에 쓰였다.

**보내기로 했다.** 이 이벤트의 쓰임이 "축이 여섯인데 실제로 뭘 쓰나 — **안 쓰는 축은 UI 에서
내릴 수 있다**" 인데(§4.2), 메이킹만 빼고 세면 그 축은 영영 판단 대상에서 빠진다.
서버는 `axis` 값을 검증하지 않으므로(키만 본다) 저장에는 문제가 없다.

✅ **해결 (2026-08-19)** — SPEC-10 §4.2 목록에 `method` 를 넣었다 (이슈 052).
화면이 이미 보내고 있었고, 목록에서 빠지면 **메이킹만 판단 대상 밖**이 된다 —
"안 쓰는 축은 UI 에서 내릴 수 있다" 가 이 이벤트의 쓰임인데 그 판단에서 한 축이 빠진다.

### G-38

**어드민에 레시피를 편집할 API 가 없다** *(이슈 047)*

`NFR-O-01` 의 인수 시나리오는 **"신규 1건을 어드민만으로 발행 완료"** 다 — 생성 · 재료 선택 ·
레시피 · 3축 · `tasting_note` · 게이트 통과 · 발행까지 개발자 개입 0. 그런데 어드민 API 에
레시피를 쓰는 자리가 없다.

```
/api/v1/admin/cocktails            생성 · 목록
/api/v1/admin/cocktails/{id}       조회 · 수정        ← 스칼라 필드뿐
/api/v1/admin/cocktails/{id}/publish · unpublish · archive
/api/v1/admin/ingredients …        재료 마스터
```

`AdminCocktailResponse` 에도 `ingredients` · `steps` 가 없다. 즉 **에디터가 어드민에서
레시피를 넣을 방법이 없고**, 발행 게이트가 레시피를 요구한다면 그 화면만으로는 영영
발행할 수 없다.

**이슈 047 이 만든 것**: 목록 · 생성 · 스칼라 편집 · 전이(발행/취소/보관) · 발행 조건 패널.
**못 만든 것**: 재료 선택(RED 22) · 스텝 편집(RED 24) · 도수 표시·오버라이드(RED 25·26) ·
인수 시나리오(RED 27).

✅ **해결 (2026-08-19)** — 이슈 051 이 `GET`·`PUT /admin/cocktails/{id}/recipe` 를 만들고
어드민에 레시피 편집을 붙였다. `AdminRecipeApiTest` 의 인수 시나리오가 **HTTP 만으로**
생성 → 재료 → 레시피 → 발행까지 간다 (`NFR-O-01`).

그 과정에서 도수 계산의 결함이 하나 드러났다. 재료 마스터에 도수가 없으면
`AbvCalculator` 가 `0` 을 돌려줬고, 진 베이스 칵테일이 `abv = 0` 으로 저장되려다
`ck_cocktail__non_alcoholic`(무알콜 ⟺ 0도)에 막혀 **500** 이 됐다. 아는 값이 하나도 없으면
`null` 이다 — "모른다" 와 "0도" 는 다르다. 시드가 SQL 로 들어와 이 경로를 아무도 안 밟았다.

### G-42

**「하나만 더」가 대체재를 모른다** *(2026-08-20)*

`R-F2.2-3` — *"부족한 재료에 국내 구매처 링크 또는 **대체재**를 제시한다."*
[내 술장](../screens/SCREENS-03_파인더.md)의 「재료 하나만 더 있으면」은 빠진 재료 **이름만**
말한다. 캄파리가 없다고 나오지만 "아페롤로도 됩니다" 를 말하지 못한다.

두 가지가 걸려 있다.

- **구매처 링크**는 국내 유통 데이터가 없어 못 한다 ([G-41](#g-41)과 같은 이유).
- **대체재**는 데이터가 있긴 하나 자리가 다르다. `data.ts` 의 `sub` 는 레시피 줄에 붙은
  문장이라 "이 칵테일에서 캄파리 대신" 을 말한다. 역검색이 필요한 것은 그 반대다 —
  **가진 것으로 채울 수 있나**. 그러려면 재료 사이의 대체 관계가 있어야 하고, 계약의
  `RecipeIngredient.substituteIngredientId` 가 그 자리다.

**남은 일**: `substituteIngredientId` 가 채워지면 `stock.ts` 의 `met()` 이 대체재까지
훑도록 넓힌다. 판정 한 곳만 고치면 되도록 이미 함수로 빼 뒀다.

### G-43

**공유 카드의 한글 글꼴을 아직 바깥에서 받는다** *(2026-08-20)*

[`lib/og-card.tsx`](../../apps/web/lib/og-card.tsx) 가 카드를 그릴 때 구글 폰트에서
**쓸 글자만** 잘라 받는다 (`text=` 파라미터). 발행분 카드는 이제 빌드 때 미리 그리므로
(`opengraph-image.tsx` 의 `generateStaticParams`) **그 왕복은 빌드에서 한 번**이고,
크롤러는 만들어 둔 파일을 받는다 — 실측 3ms.

그래도 바깥 의존이 남는다.

| 언제 | 무엇 |
|---|---|
| 빌드 | 49번(코퍼스만큼) 구글을 부른다. 막히면 카드가 라틴 글꼴로 나간다 |
| 지워진 링크 | `dynamicParams` 가 켜져 있어 요청 시 그린다 (RED 23) — 그때 다시 부른다 |
| ISR 재생성 | 발행 시 다시 그릴 때 |

지금은 3초 타임아웃 · 프로세스 안 캐시 · 받은 것이 글꼴인지 검사까지 두었다. 실패하면
라틴 글꼴로 그려진다 — 이름이 네모로 나오지만 카드가 없어지지는 않는다.

**한 벌을 리포에 넣지 못한 이유**

| | |
|---|---|
| 전체 Noto Sans KR Bold | **5.87MB** — 서버리스 번들에 얹기 어렵다 |
| 상용 한글 2350자만 잘라 달라고 | `text=` 가 **21KB** 라 구글이 400 을 준다 |
| 코퍼스에 실제로 쓰인 716자 | 112KB — 되지만 **새 칵테일 이름이 네모로 나온다** |

**남은 일**: `pyftsubset` 같은 도구로 KS X 1001 상용 한글 + 라틴을 잘라 파일로 만들어
리포에 넣는다. 그러면 바깥 의존이 0 이 된다. 크기는 실측해야 알고, 넣는 순간
`NFR-P-04`(번들 예산)와 부딪히는지도 함께 본다.

### G-44

**`sharp` 이미지 파이프라인이 한 번 물리면 서버가 돌아오지 않는다** *(2026-08-19 · CI 에서 재현)*


| 실행 | 워드마크 | OG 라우트 | `Input buffer…` |
|---|---|---|---|

| [32231499190](https://github.com/cacaocoffee/mut/actions/runs/32231499190) (`ca42e1c`) | **인라인 SVG** | `ƒ` | **0회** — OG 전부 통과 |

### G-45

**쿠키 제약이 필요한 것보다 좁게 잡혀 있을 수 있다 — 도메인을 사야 하는가**

[SPEC-07 §1.2](../spec/SPEC-07_API명세.md)가 이렇게 적었다.

> ⚠ **호스팅 제약** — 쿠키를 공유하려면 프론트와 API가 같은 상위 도메인이어야 한다.
> 예: `www.example.kr` / `api.example.kr`.

[ADR-0007](../decisions/ADR-0007-hosting.md)이 이걸 그대로 받아 **도메인을 2단계의 선행
조건**으로 두었다. 그런데 코드가 이미 다른 모양으로 가 있다.

[`app/api/admin/[...path]/route.ts`](../../apps/web/app/api/admin/[...path]/route.ts)가
적어 둔 대로 **브라우저는 API를 직접 부르지 않는다** — "다른 오리진이고 CORS를 열지 않았다".
`/api/search` · `/api/search/suggest` · `/api/events` 도 같은 모양이다.

브라우저가 Vercel 오리진만 부른다면 쿠키도 거기에만 있으면 된다.
**Spring Security는 `Cookie:` 헤더를 읽을 뿐, 그 값이 브라우저에서 어느 도메인에
저장됐는지 모른다.** 그렇다면 상위 도메인이 같아야 할 이유가 없어진다.

**막고 있는 것은 응답 쪽이다.** 지금 프록시는 상류 응답에서 `Content-Type` 만 옮기고
`Set-Cookie` 를 버린다. 로그인이 발급한 세션 쿠키가 브라우저까지 오지 못한다.

| 확인해야 하는 것 | |
|---|---|
| `Set-Cookie` 를 그대로 전달할 때 `Domain` 속성을 떼야 하는가 | 상류가 자기 도메인을 적어 보내면 브라우저가 버린다 |
| 쿠키가 여러 장일 때 | `getSetCookie()` 로 받아야 한 장만 남지 않는다 |
| `SameSite=Lax` 가 그대로 성립하는가 | 브라우저 관점에서는 동일 오리진이므로 성립할 것으로 보이나 확인 안 했다 |
| 소셜 로그인 되돌아오는 경로 | 상류가 직접 리다이렉트하면 프록시를 거치지 않는다 |

**왜 지금 올리나** — 성립하면 **도메인이 2단계를 막지 않는다.** 값 문제가 아니라 순서 문제다.

**판정 (2026-08-21) — 성립한다. 도메인 없이 2단계를 올릴 수 있다.** 표의 네 항목을 확인했다.

| 확인한 것 | 결과 |
|---|---|
| `Set-Cookie` 의 `Domain` 속성 | 뗄 것이 없다 — `SessionCookieConfig` 의 `mut.session.cookie-domain` 기본값이 빈 문자열이라 상류가 `Domain` 을 아예 안 적는다. 브라우저는 자기가 요청한 오리진(= 웹)에 쿠키를 귀속시킨다. **배포에서 이 값을 비워 두는 것이 조건이다** |
| 쿠키가 여러 장일 때 | 프록시가 `getSetCookie()` 로 전부 옮긴다 (`app/api/v1/auth/[...path]/route.ts` · 어드민 프록시) |
| `SameSite=Lax` | 성립 — 브라우저 관점에서 전부 웹 오리진과의 동일 오리진 요청이고, 카카오 → 콜백 복귀는 최상위 GET 내비게이션이라 Lax 가 쿠키를 실어 보낸다 |
| 소셜 로그인 복귀 경로 | 프록시를 거치게 만들었다 — `redirectUri()` 가 `{redirect-base}/api/v1/auth/{provider}/callback` 으로 조립되므로 **`mut.oauth.redirect-base` 를 웹 오리진으로** 주면 콜백이 웹 오리진에 떨어진다. 웹에 같은 경로 모양의 프록시(`/api/v1/auth/*`)를 만들어 글자 단위 일치를 지켰다 |

남는 배포 조건 세 가지: ① `mut.session.cookie-domain` 은 빈 값 ② `mut.oauth.redirect-base` = 웹 오리진 (제공자 콘솔에도 같은 값 등록) ③ 인가 진입도 웹 오리진 경로(`/api/v1/auth/{provider}/authorize`)로 링크한다. ADR-0007 의 2단계 선행 조건에서 도메인 구매를 뺐다.
성립하지 않으면 SPEC-07 §1.2 가 맞고 도메인을 먼저 사야 한다.

**하지 않은 것**: 코드를 고치지 않았다. 정본(SPEC-07)이 명시적으로 정한 제약이라
[CLAUDE.md](../../CLAUDE.md) 대로 맞추지 않고 여기에 올린다. 인증 화면을 만드는 이슈에서
실측으로 판정한다.

### G-46

**콘텐츠 사진을 컬러로 낸다 — 시안의 흑백 규칙을 뗀다**

✅ **해결 (2026-08-20)** — [ADR-0008](../decisions/ADR-0008-color-photos.md).

**무엇을 어기나** — 시안 원본 `docs/design/source/MUT.dc.html:267`이 *"사진은

### G-48

**Lighthouse 를 배포 차단에서 경고로 내린다**

[SPEC-04 §9.1](../spec/SPEC-04_비기능요구사항.md)이 `NFR-P-01~03`(LCP 예산)을 **배포 차단**으로
정했고 `web-quality.yml` 이 그대로 걸고 있었다. 이것을 경고로 내린다 — 스펙과 CI 가
다른 말을 하지 않도록 여기 등재한다 (SPEC-00 §4).

**무엇이 있었나** — 매거진판([ADR-0009](../decisions/ADR-0009-design-magazine.md))으로 바꾼 뒤
CI 에서 상세 3,028ms · 탐색 3,590ms 가 나와 예산 2,500ms 를 넘겼다.

**측정을 믿을 수 없다는 것이 문제다.** 같은 빌드를 로컬에서 재니 같은 화면이 **1.6초와
3.9초** 로 나왔다. 그 폭이면 통과 여부가 코드가 아니라 그날 기계 사정으로 갈린다.
2코어 러너가 `localhost` 를 재는 값이라 실사용자 성능의 대리치로도 약하다.

**글꼴 탓이 아니다** — 처음에 그렇게 봤는데 리포트가 아니라고 했다. 글꼴 파일은
559~1,067ms 에 전부 도착하는데 LCP 는 그 뒤로 한참이다. `font-display` 는 533개 전부
`swap` 이고 `TBT` 는 0ms, `Load Time` 도 0ms 다. **원인을 아직 모른다.**

**기계가 놀 때는 통과한다.** 다른 것을 안 돌리고 다시 재니 다섯 화면 전부 0.9~1.5초였다.
3.9초가 나온 실행은 같은 기계에서 e2e 와 도커를 함께 돌리던 중이었다. **CI 2코어와
실사용자 휴대폰은 놀고 있는 개발 기계보다 그 바쁜 쪽에 가깝다** — 그래서 측정을 버리는
것이 아니라 막는 자리에서만 뺀다.

| | |
|---|---|
| 남는 것 | 상세가 글꼴 **43요청 · 688KB** 를 받는다. `unicode-range` 는 제대로 돈다(내용에 따라 19~43으로 달라진다). 다만 한글 세리프 두 벌의 값이라 줄일 여지가 있다 |
| 안 한 것 | 실사용자 기준 측정(RUM). 배포된 주소가 생겼으므로 이제 붙일 수 있다 |

**숫자는 계속 찍는다.** 나빠지는 것을 안 보겠다는 것이 아니라 머지를 막는 자리에서
빼는 것이다. 되돌리는 조건은 **실사용자 측정이 붙었을 때** — 그때 무엇을 차단으로 걸지
그 데이터로 다시 정한다.

### G-49
**아티클 주제 축과 발행 형식 축의 관계 미결** (2026-08-20 · [ADR-0010](../decisions/ADR-0010-articles-over-my-bar.md)).
화면은 주제 축 `cocktail`(칵테일) · `bar`(바) · `spirits`(스피릿)의 세 갈래로 아티클을 나누는데
(처음엔 `whisky` 위스키였다가 진·꼬냑·소주 리뷰가 들어오며 2026-08-21 스피릿으로 넓혔다),
SPEC-02 §6 의 `Article.type` 은 발행 형식 축(`interview`·`guide`·`trend`·`photo_essay`)이다.
두 축을 다 둘지, 하나로 합칠지, 매핑할지는 `GET /articles` 계약을 만들 때 정한다.
그때까지 주제 축은 `packages/domain/src/articles/` 안의 화면 전용 값이다.

### G-50
**KPI 「내 술장 3개+ 등록 유저 → 가입자 25%」의 대체 지표 미결** (2026-08-20 ·
[ADR-0010](../decisions/ADR-0010-articles-over-my-bar.md)). 내 술장이 폐기돼
이 지표는 잴 수 없다.

**대체 지표 (2026-08-25 정함) — 콘텐츠 가설을 두 눈금으로 잰다.** 계측을 붙였다:

| 지표 | 이벤트 | 뜻 |
|---|---|---|
| **아티클 유기 유입** | `article_view` 의 `entryPoint = external` 비율 | 아티클이 검색으로 읽히나 (cocktail_view 와 같은 눈금) |
| **콘텐츠 → 칵테일 전환** | `cocktail_view` 의 `entryPoint = article` 건수 | 읽은 사람이 실제로 칵테일로 넘어가나 |

가입자 전환(25%)은 회원 기능이 아직 없어(북마크가 Phase 2) 지금 잴 수 없다 — 그때
`bookmark_add` 로 잇는다. 그전까지는 위 두 눈금이 "콘텐츠가 유입을 만드는가"를 대신 답한다.
목표 수치는 실데이터가 한 달 쌓인 뒤 정한다 — 지금 정하면 근거 없는 숫자다.
