## 1. 역할

네 개다. 더 늘리지 않는다 — 역할이 늘면 조합이 폭발하고 아무도 전체를 이해하지 못한다.

| 역할 | 누구 | 무엇을 하나 |
|---|---|---|
| `member` | 일반 사용자 | 저장 · 컬렉션 · 내 술장 |
| `editor` | 에디터 | 콘텐츠 작성 · 발행 · 검증 태스크 처리 |
| `partner_owner` | 제휴 바 오너 | **자기 바에 한정해** 정보 관리 · 통계 조회 |
| `admin` | 관리자 | 제휴 등급 · 재료 승인 · 감사 로그 |

역할은 **누적되지 않는다.** `editor`가 `admin` 권한을 갖지 않는다.
한 사람이 둘 다 필요하면 계정에 역할을 복수로 부여한다(`user_role` 다대다).

### 1.1 비로그인

콘텐츠 조회는 전부 비로그인으로 가능하다. **인터스티셜을 세우지 않는다**
(`PRIN-T04` · [ADR-0004](../decisions/ADR-0004-age-gate.md)).

내 술장은 로그인 없이 **로컬 저장으로 체험**할 수 있고, 저장 시점에 로그인을 유도한다 (`R-F2.2-4`).

### 2.1 마지막 줄이 요점이다

**노출 규칙(부스팅 한도 · 홈 슬롯 비율)은 `admin`도 못 바꾼다.**
API 표면에도 DB 컬럼에도 존재하지 않는다 (`PRIN-P02` · `FR-ADMIN-006`).

바꾸려면 코드를 고치고 배포해야 한다. 그게 의도다 — 영업 압박이 들어오는 순간
"어드민에서 잠깐만"이 가능하면 반드시 그렇게 된다.

### 2.2 등급 변경을 `editor`에게 주지 않는 이유

`editor`는 큐레이션 리스트를 만드는 사람이고, `partner_tier`는 매출과 직결된다.
한 사람이 둘 다 쥐면 `R-F3.3-3`(순위에 제휴 영향 없음)의 감시자가 사라진다.
**권한 분리 자체가 중립성 장치다.**

## 3. 스코프 — `partner_owner`

### 3.1 소유 관계가 필요하다

`partner_owner`가 "자기 바"를 판정하려면 **사용자와 바를 잇는 관계**가 있어야 한다.
[SPEC-06](./SPEC-06_데이터모델_ERD.md)에 `partner_contract(bar_id, tier)`는 있지만
`user ↔ bar` 연결이 없었다. **이 문서를 쓰면서 발견한 누락**이라 스키마를 보강한다.

```
bar_owner
  user_id   BIGINT  FK → user
  bar_id    BIGINT  FK → bar
  granted_by BIGINT FK → user      -- 누가 부여했나
  granted_at TIMESTAMPTZ
  PK (user_id, bar_id)
```

한 사람이 여러 바를 소유할 수 있고(체인), 한 바에 오너가 여럿일 수 있다(공동 운영).

### 3.2 검증 규칙

**경로의 `barId`를 신뢰하지 않는다.** 모든 `/partner/**` 요청에서:

1. 세션의 `userId`를 가져온다
2. `bar_owner`에 `(userId, barId)` 행이 있는지 확인한다
3. 없으면 **`404`** 로 응답한다 — `403`이면 "그 바가 존재한다"는 사실이 새어나간다

```
GET /partner/bars/{barId}/stats
  → bar_owner 검증 실패 시 404
```

이게 IDOR(Insecure Direct Object Reference)의 표준 방어다.
`barId`를 1씩 바꿔가며 남의 통계를 긁는 시도가 막힌다.

### 3.3 등급별 차등

| 등급 | 정보 수정 | 메뉴판 | 통계 |
|---|---|---|---|
| `listed` | 수정 **요청**만 | — | — |
| `verified` | 직접 수정 | — | 기본 |
| `partner` | 직접 수정 | ○ | 전체 + 유입 칵테일 랭킹 |
| `signature` | 직접 수정 | ○ | 전체 |

등급은 `partner_contract.tier`에서 읽고, **`partner_until` 경과 시 자동 강등**된다
(`FR-PARTNER-001`). 강등은 세션에 캐시하지 않는다 — 다음 요청부터 즉시 적용돼야 한다.

httpOnly 쿠키 세션을 고른 이유 중 하나가 이것이다. JWT였다면 access 토큰 만료까지 지연된다
([SPEC-07 §1.2](./SPEC-07_API명세.md)).

## 4. 인증

### 4.1 세션

| 항목 | 값 |
|---|---|
| 저장 | 서버 세션 (Spring Session) |
| 쿠키 | `httpOnly` · `Secure` · `SameSite=Lax` |
| 수명 | 일반 30일 rolling · **`editor`/`admin` 8시간 절대** |
| 무효화 | 로그아웃 · 역할 변경 · 차단 시 즉시 |

어드민 세션을 짧게 두는 이유는 **발행 권한이 곧 콘텐츠 신뢰**이기 때문이다.
공용 PC에 남은 세션으로 아무나 발행할 수 있으면 안 된다.

### 4.2 소셜 로그인

카카오 · 네이버 · 애플. OAuth 2.0 Authorization Code + PKCE.

```
GET  /auth/{provider}/authorize   → state 발급, provider로 리다이렉트
GET  /auth/{provider}/callback    → state 검증 → 세션 발급
```

- `state`는 1회용, 10분 만료. 재사용 시도는 거부하고 로그한다.
- provider가 이메일을 주지 않을 수 있다(애플 비공개 릴레이). **이메일을 필수로 만들지 않는다.**
- 동일인 판정은 `(provider, provider_uid)`다. 이메일로 계정을 병합하지 않는다 —
  이메일은 provider마다 다를 수 있고 변경될 수 있다.

### 4.3 CSRF

쿠키 인증이므로 CSRF 방어가 필수다.

- 상태 변경(`POST`·`PATCH`·`PUT`·`DELETE`)은 `X-CSRF-Token` 헤더를 요구한다
- 토큰은 `GET /auth/csrf`가 발급, 세션에 바인딩
- `SameSite=Lax`가 1차 방어, CSRF 토큰이 2차

`POST /events`(이벤트 수집)는 예외다 — 인증이 필요 없고 부작용이 집계뿐이라
CSRF 대신 레이트 리밋으로 방어한다.

## 5. 개인정보

### 5.1 수집 항목

| 항목 | 출처 | 필수 | 왜 |
|---|---|---|---|
| `provider` + `provider_uid` | 소셜 | ✅ | 동일인 판정 |
| `display_name` | 소셜 | ✅ | 화면 표시 |
| `email` | 소셜 | — | 공지. 없어도 가입 가능 |
| 북마크 · 컬렉션 | 사용자 | — | `R-F5-2` |
| 내 술장 재료 | 사용자 | — | `R-F2.2-1` |

**수집하지 않는 것** — 생년월일(성인 인증 폐기, [ADR-0004](../decisions/ADR-0004-age-gate.md)),
전화번호, 주소, 결제 정보.

### 5.2 위치 정보

**저장하지 않는다** (`PRIN-D04`). "내 주변 바" 기능은 브라우저 좌표를 받아
그 요청에서만 쓰고 버린다. DB 컬럼도 로그도 남기지 않는다.

거리 계산은 서버가 하되 **좌표를 로그에 남기지 않도록** 요청 로깅에서 해당 파라미터를 마스킹한다.

### 5.3 탈퇴 · 파기

| 데이터 | 처리 |
|---|---|
| `user` 행 | 즉시 삭제 |
| 북마크 · 컬렉션 · 내 술장 | 즉시 삭제 (CASCADE) |
| `analytics_event.user_id` | **`NULL`로 익명화** — 행은 남긴다 |
| `audit_log.actor_user_id` | 유지 — 누가 발행했는지는 기록이다 |
| `bar_owner` | 삭제 |

`analytics_event`를 지우지 않는 이유는 집계 지표가 소급 변동하면 안 되기 때문이다.
`user_id`만 끊으면 개인 식별성이 사라진다.

`audit_log`는 예외로 둔다 — 콘텐츠 발행 이력은 **법적 근거이자 신뢰 기록**이고,
`PRIN-T08`이 요구한 감사 가능성의 대상이다. 이 예외는 개인정보 처리방침에 명시한다.

### 5.4 파트너 통계와 개인정보

파트너 대시보드는 **집계값만** 돌려준다. 개별 사용자를 식별할 수 있는 어떤 값도 넣지 않는다.

`R-F4.3-2` 유입 칵테일 랭킹도 `(칵테일, 유입 수)` 쌍일 뿐 누가 왔는지는 담지 않는다.

## 6. 레이트 리밋

| 대상 | 한도 | 기준 |
|---|---|---|
| 공개 조회 API | 300 req/min | IP |
| `/search` · `/search/suggest` | 60 req/min | IP |
| `/events` | 120 req/min | 세션 |
| `/auth/*/callback` | 10 req/min | IP |
| 어드민 쓰기 | 60 req/min | 사용자 |

초과 시 `429` + `Retry-After`.

검색을 더 조이는 이유는 초성·별칭 매칭이 GIN 인덱스를 타긴 해도
**가장 비싼 조회**이기 때문이다 ([SPEC-06 §5](./SPEC-06_데이터모델_ERD.md)).

## 7. 주요 위협과 방어

| 위협 | 방어 |
|---|---|
| XSS로 세션 탈취 | `httpOnly` 쿠키 — JS가 읽을 수 없다 |
| CSRF | `SameSite=Lax` + CSRF 토큰 |
| **IDOR** (남의 바 통계 조회) | `bar_owner` 검증 후 실패 시 **404** (§3.2) |
| 비공개 리소스 존재 노출 | `draft`·미소유 리소스는 전부 `404` |
| 대량 크롤링 | 레이트 리밋 + `analytics_event` 이상 탐지 |
| 발행 권한 오용 | 어드민 세션 8시간 + 전 건 감사 로그 |
| 저장 XSS (에디터 입력) | 본문은 마크다운 → 서버에서 sanitize 후 저장 |
| SQL 인젝션 | JPA 파라미터 바인딩. **초성 검색도 `LIKE` 파라미터로 처리** |

에디터 입력을 sanitize하는 지점을 **저장 시점**으로 잡은 이유는, 렌더링 시점에만 처리하면
SSG 빌드·어드민 미리보기·OG 태그 생성 등 출력 경로마다 놓칠 수 있기 때문이다.

## 8. 법적 요구

[ADR-0004](../decisions/ADR-0004-age-gate.md)로 성인 인증은 폐기됐다. 남은 것:

| 요구 | 어디서 |
|---|---|
| 과음 경고 문구 고정 노출 | 전 페이지 하단 (`R-F1.1-8`) |
| `제휴 콘텐츠` 라벨 | `article.is_sponsored` 기반, 렌더링 강제 (`R-F4.2-3`) |
| 브랜디드 콘텐츠 주류광고 고지 | `FR-USER-002` |
| 미성년자 대상 광고 금지 | **광고 운영 규칙** — 시스템 기능이 아니다 |
| 개인정보 처리방침 · 이용약관 | 정적 페이지 |

**법률 검토 1회가 미완이다** (PRD 15장). 검토 항목:

1. 전면 성인 인증이 실제로 요구되는가 (ADR-0004의 전제)
2. 브랜디드 콘텐츠의 주류광고 기준 적용 범위
3. `audit_log` 보존을 개인정보 파기 예외로 두는 것의 적법성
