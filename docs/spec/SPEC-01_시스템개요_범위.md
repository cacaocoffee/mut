## 1. 한 줄 정의

> 구조화된 칵테일 레시피 DB와 에디토리얼 바 큐레이션을 **하나의 그래프로 연결**해,
> 칵테일에서 바로 · 바에서 칵테일로 이어지는 순환을 만드는 발견 레이어.

## 2. 도메인 코드

모든 요구사항 ID · API 경로 · 모듈 경계가 이 코드를 쓴다.

| 코드 | 도메인 | 무엇을 책임지나 |
|---|---|---|
| `COCKTAIL` | 칵테일 | 칵테일 · 레시피 · 분류 3축 · 향과 맛 |
| `INGREDIENT` | 재료 | 재료 마스터 · 국내 유통 · 대체재 |
| `BAR` | 바 | 바 정보 · 영업시간 · 메뉴 · 바텐더 |
| `PARTNER` | 제휴 | 등급 · 전용 콘텐츠 · 대시보드 · 노출 규칙 |
| `CONTENT` | 콘텐츠 | 아티클 · 큐레이션 리스트 |
| `USER` | 사용자 | 소셜 인증 · 저장 · 컬렉션 · 프로필 |
| `STOCK` | 내 술장 | 보유 재료 · 역검색 |
| `SEARCH` | 검색 | 통합 검색 · 별칭 · 초성 · 패싯 |
| `ADMIN` | 어드민 | 발행 워크플로 · 검증 태스크 · 감사 로그 |

## 3. 시스템 경계

```
                     ┌─────────────────────────────┐
   검색엔진 · 사용자 ──▶│  apps/web  (Next.js 16)     │
                     │   · SSG/ISR 공개 페이지       │
                     │   · 필터 (클라이언트)          │
                     │   · /admin 에디터 UI          │
                     └──────────────┬──────────────┘
                                    │ REST /api/v1/*
                                    │ (OpenAPI 계약)
                     ┌──────────────▼──────────────┐
                     │  apps/api  (Kotlin/Spring)  │
                     │   모듈러 모놀리스 9개 모듈      │
                     │   · 도메인 불변식 강제         │
                     │   · 발행 워크플로              │
                     └──────┬───────────────┬──────┘
                            │               │
                  ┌─────────▼──────┐  ┌─────▼──────────────┐
                  │  PostgreSQL 16 │  │  외부 어댑터        │
                  └────────────────┘  │  지도 · 예약 · 소셜 │
                                      │  인스타 피드        │
                                      └────────────────────┘
```

**프론트는 DB를 직접 보지 않는다.** SSG 빌드 시점에도 API를 통한다 —
그래야 계약이 하나로 유지되고 어드민·배치가 같은 규칙을 쓴다 (`PRIN-T02` · `PRIN-T05`).

## 4. Phase 1 범위 — 1a · 1b로 나눈다

PRD 14장의 MVP(M0–M3)를 **두 단계로 쪼갠다.** 스펙은 전부 쓰여 있고 순서만 나눈다.

### 4.1 Phase 1a — 칵테일 아카이브 단독

**P0 56건.** 바 없이 성립하는 전부.

| 도메인 | 들어가는 것 | P0 |
|---|---|---|
| `COCKTAIL` | 분류 3축 · 상세(향과 맛 포함) · 레시피 버전 · 잔 수 환산 · 카테고리 페이지 | 27 |
| `SEARCH` | 필터 + 패싯 카운트 · 한/영 별칭 · 초성 | 9 |
| `ADMIN` | 에디터 CMS · 발행 워크플로 · 발행 게이트 | 8 |
| `INGREDIENT` | 재료 마스터 · 대체재 · 국내 유통 표기 | 6 |
| `USER` | 소셜 로그인 · 저장 · 컬렉션 공유 | 6 |

**1a의 성패는 콘텐츠와 검색 유입이다.** 칵테일 100종을 발행하고
유기 검색이 실제로 들어오는지 본다.

### 4.2 Phase 1b — 그래프 완성

**P0 21건.** 스펙은 [SPEC-02](./SPEC-02_도메인모델.md) · [SPEC-06](./SPEC-06_데이터모델_ERD.md) ·
[SPEC-07](./SPEC-07_API명세.md)에 **이미 작성돼 있다.** 착수 시점만 미뤘다.

| 도메인 | 들어가는 것 | P0 |
|---|---|---|
| `BAR` | 상세 · 목록 · 지도 · 시그니처 메뉴 | 14 |
| `PARTNER` | Listed · Verified 등급 (수기 운영) | 7 |

### 4.3 이 분할의 비용

**`PRIN-P01`(그래프가 제품이다)이 1b까지 검증되지 않는다.**

칵테일↔바 양방향 연결이 이 제품의 해자이고, PRD 2.2가 크로스 이동률을
"진짜 검증 지표"로 지목했다. 1a만으로는 **레시피 사이트와 구별되지 않는다.**

의식적으로 지불하는 비용이다. 1a에서 확인할 수 있는 것은 그래프 가설이 아니라
**콘텐츠 품질과 SEO 가설**이다. 그 둘이 먼저 서지 않으면 바를 붙여도 유입이 없다.

### 4.4 이후

## 6. 현재 구현 상태

`apps/web`에 **프로토타입**이 있다. 칵테일 24종이 TypeScript 정적 배열에 있고
탐색 · 상세 · 파인더 3개 화면이 동작한다.

이 프로토타입의 역할은 두 가지다.

1. **디자인 시스템이 실제로 성립하는지에 대한 증명** — Modernist 토큰 위에서 3개 화면이 돌아간다.
2. **분류 3축과 패싯 카운트의 동작 검증** — `R-C-1` · `R-C-3` · `R-F2.1-2`가 구현 가능한 형태인지.

**API 연동 시점에 정리되는 것:**

| 지금 | 이후 |
|---|---|
| `packages/domain/src/data.ts` 24종 | Postgres 시드 데이터로 이관 |
| `packages/domain/src/types.ts` | OpenAPI 생성 타입으로 대체 (`PRIN-T02`) |
| `packages/domain/src/validate.ts` | Kotlin으로 이관 — 발행 게이트는 서버가 강제 (`PRIN-T05`) |
| `packages/domain/src/search.ts` 필터 로직 | 클라이언트 필터로 유지, 패싯 카운트는 서버 응답 사용 |
| `packages/ui` | 그대로 유지 |

## 7. 이해관계자

| 역할 | 이 시스템에서 무엇을 하나 |
|---|---|
| 홈텐더 (P1) | 레시피를 찾고 만든다. 내 술장으로 역검색한다 (Phase 2) |
| 바 탐험가 (P2) | 바를 찾고 저장한다. 시그니처에서 레시피로 넘어간다 |
| 제휴 바 오너 (P3) | 자기 바 정보를 관리하고 유입 데이터를 본다 |
| 에디터 | 콘텐츠를 쓰고 발행한다. **개발자 없이** (PRD 12장) |
| 관리자 | 제휴 등급 · 검증 태스크 · 감사 로그를 다룬다 |

권한 스코프는 [SPEC-08 보안·권한](./SPEC-08_보안_권한_개인정보.md)에서 정의한다
([G-11](../prd/GAPS.md#g-11) 해소 대상).

### 8.1 Phase 1a

| 조건 | 측정 |
