# SPEC-00 — 개발 원칙 (Constitution)

| | |
|---|---|
| 버전 | v1.0 |
| 최종 수정 | 2026-08-06 |
| 상위 문서 | [PRD v1.1](../prd/MUT_PRD_v1.md) |

이 문서는 **다른 모든 SPEC보다 우선한다.** 하위 문서가 여기와 충돌하면 하위 문서가 틀린 것이다.
원칙을 바꾸려면 이 문서를 먼저 고치고 개정 이력을 남긴다.

원칙은 `PRIN-P`(제품) · `PRIN-T`(기술) · `PRIN-D`(데이터) 세 갈래다.

---

## 1. 제품 원칙 (PRIN-P)

### PRIN-P01 — 그래프가 제품이다

칵테일 DB와 바 DB를 따로 만들면 이 제품은 존재 이유가 없다. 레퍼런스 네 곳(Difford's · Punch ·
50 Best · 네이버 지도)이 이미 각 축을 따로 하고 있고, 우리가 더 잘할 이유가 없다.

**칵테일 상세 → 이 칵테일을 잘 만드는 바**, **바 상세 → 이 바의 시그니처 레시피**.
이 양방향 순환이 해자이고 제휴 상품의 근거다.

- 새 기능을 넣을 때 "이게 그래프를 굵게 하는가"를 먼저 묻는다.
- 검증 지표는 트래픽이 아니라 **크로스 이동률**이다 (PRD 2.2). 이걸 못 세면 가설을 못 본다.

### PRIN-P02 — 큐레이션 중립성은 하드 제약이다

영업 편의로 조정할 수 있게 만들면 **반드시 조정된다.** 어드민에 수치 입력란을 두는 순간
그 수치는 올라간다. 그러므로 아래는 코드 상수로 박고, 어드민에서 노출하지 않는다.

| 제약 | 근거 |
|---|---|
| 정렬 상위 3개 중 파트너 부스팅 최대 1개 | `R-F4.2-2` |
| 홈 파트너 슬롯 ≤ 전체의 30% | `R-F4.2-4` |
| 순위형 리스트에서 제휴 여부가 순위에 영향 없음 | `R-F3.3-3` |
| 유료 대가 콘텐츠에 `제휴 콘텐츠` 라벨 상단 표기 | `R-F4.2-3` — 공정위 심사지침상 **의무** |

라벨을 축소하거나 흐리게 처리하는 스타일 변경도 이 원칙 위반이다.

### PRIN-P03 — 만들어보지 않은 것은 쓰지 않는다

`R-F1.1-2`가 향과 맛을 발행 필수로 잡은 이유다. 다른 사이트 설명을 옮기면 레시피 나열형
블로그와 구별되지 않고, 그 순간 이 서비스의 존재 이유가 사라진다.

- 향과 맛 서술이 비면 **발행 자체가 불가능**해야 한다. 경고가 아니라 차단이다 (`PRIN-T05`).
- 표준 레시피는 만들어보고 발행한다. 검증 없는 레시피 하나가 신뢰 전체를 무너뜨린다.

### PRIN-P04 — 별점을 쌓지 않는다

총점·평균을 만들지 않고 노출하지 않는다 (`R-F3.1-4`). 신뢰 신호는 에디터 큐레이션 여부와
수상 이력이다. 부정적 평가는 싣지 않되 칭찬도 하지 않는다 — **큐레이션에서 제외하는 것으로
의견을 표현한다.** 소규모 자영업자를 다루는 서비스에서 공개 비판은 리스크 대비 실익이 없다.

### PRIN-P05 — 국내 기준으로 정규화한다

이 서비스가 해외 DB의 번역판이 아닌 이유는 `domestic_availability` 하나다.
국내에서 못 구하는 재료는 대체재를 필수로 단다 (`R-F1.3-2`).

### PRIN-P06 — 카테고리와 필터는 다른 것이다

이 구분이 무너지면 URL 구조와 SEO가 함께 무너진다.

| | 카테고리 | 필터 |
|---|---|---|
| 무엇 | 기주 · 스타일 · 메이킹 방법 3축 | 당도 · 도수 · 향과 맛 · 보유 재료 |
| 형태 | 경로 `/cocktails/base/gin/` | 쿼리스트링 `?sweet=1&flavor=citrus` |
| 색인 | 한다 | **하지 않는다** (`noindex`) |
| 필수성 | 모든 칵테일이 반드시 하나씩 (`R-C-1`) | 없어도 됨 |

당도나 도수를 카테고리로 올리면 `/cocktails/sweet/high-abv/gin/` 같은 조합 폭발이 생기고
중복 콘텐츠로 SEO 페널티를 받는다. **축 조합 경로는 만들지 않는다** (`R-C-2`).

## 2. 기술 원칙 (PRIN-T)

### PRIN-T01 — 확정 스택 준수

| 층 | 선택 |
|---|---|
| 백엔드 | **Kotlin + Spring Boot 3.x** (Spring Web · Data JPA · Security · Batch) |
| DB | **PostgreSQL 16** |
| 프론트엔드 | **Next.js 16 (App Router) + TypeScript** |
| 어드민 | Next.js 앱 내부 (`/admin`) — API를 소비하는 별도 라우트 그룹 |
| 디자인 시스템 | 매거진판 (`packages/ui`) — [ADR-0009](../decisions/ADR-0009-design-magazine.md) |

임의로 다른 스택을 들이지 않는다. 필요하면 이 표를 먼저 고친다.

### PRIN-T02 — 계약이 정본이다 (Contract-First)

**언어가 둘이라 분류 축과 DTO가 두 곳에 존재한다. 손으로 양쪽을 맞추면 반드시 어긋난다.**

- **OpenAPI 스펙이 단일 진실 공급원이다.** Spring이 생성하고, 프론트의 TS 타입은 거기서 뽑는다.
- 손으로 쓴 TS DTO를 두지 않는다. 생성물은 커밋하되 손으로 고치지 않는다.
- 분류 축 enum(`BaseSpirit` · `StyleKey` · `FlavorKey` · `SweetLevel` · `Technique`)의 정본은
  **Kotlin 쪽**이다. 현재 `packages/domain/src/types.ts`는 프로토타입 산물이며,
  API 연동 시점에 생성물로 대체한다.
- 계약이 깨지면 빌드가 깨져야 한다. 런타임에 발견하지 않는다.

### PRIN-T03 — 모듈러 모놀리스 우선

Spring 단일 배포로 시작하되 도메인 모듈 경계를 코드로 지킨다.
`cocktail` · `ingredient` · `bar` · `partner` · `content` · `user` · `stock` · `search` · `admin`.

- 모듈 간 호출은 공개 인터페이스로만. 다른 모듈의 리포지토리·엔티티를 직접 참조하지 않는다.
- 마이크로서비스로 쪼개지 않는다. 개발 1~2명 규모에서 운영 부담이 이득을 넘는다.
- 쪼갤 필요가 생기면 모듈 경계가 그대로 서비스 경계가 된다.

### PRIN-T04 — SEO 경로는 정적 우선

검색 유입이 초기 성장의 절반이다 (PRD 2.2 — 유기 검색 50% 이상).

- 칵테일 상세 · 바 상세 · 카테고리 페이지는 **SSG + ISR**. 요청 시 렌더하지 않는다.
- 필터 결과는 클라이언트에서 처리하고 `noindex`. 서버 왕복을 만들지 않는다.
- **콘텐츠 앞에 인터스티셜을 세우지 않는다.** 크롤러가 콘텐츠를 못 보면 SEO 요구와 정면 충돌한다.
  전면 성인 인증 게이트를 폐기한 이유가 이것이다 ([ADR-0004](../decisions/ADR-0004-age-gate.md)).

### PRIN-T05 — 불변식은 서버에서 강제한다

프론트 검증은 **UX용 중복**이다. 없어도 데이터가 깨지지 않아야 한다.

발행 게이트와 도메인 불변식은 서버 트랜잭션 안에서 검사한다.

| 불변식 | 근거 |
|---|---|
| 카테고리 3축 NOT NULL | `R-C-1` |
| `style_primary ∈ styles` | `R-C-3` |
| 향·맛 태그 1~3개 | `R-F1.2-1` |
| 향과 맛 서술 없으면 `published` 전이 불가 | `R-F1.1-2` · `PRIN-P03` |
| 재료는 마스터 참조 (프리텍스트 금지) | `R-F1.1-1` |

현재 `packages/domain/src/validate.ts`가 하는 일이며, **API 연동 시점에 Kotlin으로 옮긴다.**
프론트 쪽은 남겨도 되지만 그때는 보조 수단이지 근거가 아니다.

### PRIN-T06 — 외부 연동은 어댑터로 격리한다

지도(카카오/네이버) · 예약(캐치테이블·테이블링·네이버) · 소셜 로그인(카카오·네이버·애플) ·
인스타그램 피드. 전부 인터페이스 뒤에 두고 도메인이 벤더를 모르게 한다.

벤더는 바뀐다. 구글맵을 배제한 이유(국내 도보 길찾기·POI 정확도)가 바뀔 수도 있다.

### PRIN-T07 — 부수효과는 멱등하게

조회수 집계 · 쿠폰 사용 · 알림 발송 · 크롤링은 재시도가 전제다.
같은 요청이 두 번 와도 결과가 같아야 한다. 클라이언트가 멱등키를 보낸다.

### PRIN-T08 — 감사 가능성

아래는 누가 · 언제 · 무엇을 바꿨는지 이력을 남긴다. 되돌릴 수 있어야 하고, 다툼이 생겼을 때
근거가 돼야 한다.

- 콘텐츠 발행 상태 전이 (`draft` → `published` → `archived`)
- 제휴 등급 변경 (`partner_tier`)
- 큐레이션 리스트 발행 · 순위 변경
- 바 정보 검증 (`hours_verified_at`)

## 3. 데이터 원칙 (PRIN-D)

### PRIN-D01 — 재료는 참조지 문자열이 아니다

`R-F1.1-1`. 재료를 문자열로 저장하면 **역검색(내 술장)과 바 연결이 전부 불가능해진다.**
나중에 정규화하면 마이그레이션 비용이 크다. 처음부터 `ingredient_id` 참조로 간다.

`counts_for_stock` 플래그로 가니시·얼음·물을 역검색 판정에서 뺀다 (`R-F2.2-5`).
이게 없으면 민트 잎 하나 없다고 모히토가 안 나온다.

### PRIN-D02 — 슬러그는 불변이다

카테고리 슬러그는 노출되는 순간 URL이고, 바꾸면 리다이렉트 부채가 된다.
확정본은 [ADR-0002](../decisions/ADR-0002-taxonomy.md)에 있다.

새 슬러그를 추가하는 것은 자유지만 **기존 슬러그를 바꾸거나 재사용하지 않는다.**

### PRIN-D03 — Cocktail과 Recipe를 분리한다

하나의 칵테일에 에디터 표준 1개 + 제휴 바 버전 n개가 공존해야 한다 (`R-F1.1-7`).
이게 파트너 상품의 핵심이고, 나중에 분리하면 마이그레이션 비용이 크다.

### PRIN-D04 — 위치 정보는 저장하지 않는다

세션 내 사용만 한다 (PRD 12장). 유저의 좌표를 DB에 쓰지 않는다.

### PRIN-D05 — 삭제는 상태 전이다

콘텐츠와 바는 물리 삭제하지 않는다. 폐업한 바도 기록으로 남긴다 — 검색 유입이 이미 붙어 있고,
`R-F3.1-5`가 커버리지를 영업 파이프라인으로 규정했다.

## 4. 이 원칙을 어기는 법

원칙은 지키라고 있지만, 지킬 수 없는 상황이 온다. 그때는:

1. 어긴다는 사실을 [`GAPS.md`](../prd/GAPS.md)에 올린다.
2. 왜 어겼는지 ADR로 남긴다.
3. 되돌리는 조건을 함께 적는다.

**조용히 어기지 않는다.** 그게 유일한 금지 사항이다.
